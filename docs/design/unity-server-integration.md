## §1. 표시명(displayName) UX

리더보드·서버에 노출되는 플레이어 이름을 정하는 방식이다.

### 결정 (확정안)

**자동 기본명 부여 + 마을에서 1탭 변경 가능** (입력 강제 화면 없음).

> **표시명 영속 단정**: 표시명은 **로컬 전용 + 리더보드 제출 시 동봉**이다. 클라우드 세이브 본문(`MetaProfileDto`)에 displayName 필드가 없으므로(spec §4) PUT /save 로 보내도 서버가 보관하지 않고, GET /save 복원으로도 표시명은 돌아오지 않는다. **결과 UX — 기기를 옮겨 클라우드에서 복원하면 진행도는 그대로지만 표시명은 기본명으로 리셋되며, 원하면 마을에서 다시 변경한다.**

| 항목 | 결정값 | 근거 |
|---|---|---|
| 기본명 포맷 | `영주 #` + deviceId 앞 4자(대문자 16진) | 게임 세계관("던전 주인 = 영주") 일관. plan 의 임시값 `Lord-xxxx` 를 정식 한글 포맷으로 승격 |
| 예시 | `영주 #A3F9` | deviceId(GUID "N" 포맷)의 앞 4자를 대문자화 |
| 최초 입력 강제 | **없음** (게임 흐름 차단 금지 — YAGNI) | v0.3 가설은 "경쟁 동기" 검증이지 "닉네임 작명 UX" 검증이 아님 |
| 변경 진입 | 마을 "클라우드" 메뉴 팝업 안의 "표시명 변경" 버튼 1개 | 별도 닉네임 화면 신설 안 함 — 클라우드 팝업에 흡수 |
| 변경 UI | TMP_InputField 1줄 + 확인/취소 (CHButton) | Rule 03 §3 — 입력은 TMP_InputField, 버튼은 CHButton |
| 글자 수 | 1~12자 (공백 trim 후) | 리더보드 셀 이름 컬럼 폭(§4)에 12자 한글이 들어가는 상한. 0자(빈/공백뿐)면 저장 거부 |
| 허용 문자 | 제한 없음(서버가 받는 그대로). 단 앞뒤 공백 trim | v0.3 욕설 필터·중복 검사 없음(서버 미제공) — YAGNI |
| 저장 위치 | **로컬 전용** — `MetaProfile` 로컬 필드 `DisplayName`(또는 PlayerPrefs). 클라우드 본문(`MetaProfileDto`)에는 displayName 필드가 없어 백업/복원으로는 오가지 않는다 | spec §4 의 `MetaProfileDto` 필드 목록에 displayName 없음 = 확정 사실. 표시명은 로컬 보관 + 리더보드 제출 시에만 동봉 |
| 클라우드 복원 시 | 표시명은 복원으로 돌아오지 않는다 — **새 기기에서는 기본명(`영주 #xxxx`)으로 시작.** 기기 이전 후 원하면 마을에서 다시 변경 | displayName 은 서버가 leaderboard_entries 에만 저장(프로필 본문 미포함). 기기 복원은 진행도만 복원 |
| 미설정(빈 값) 시 | 제출·표시 모두 기본명(`영주 #xxxx`)으로 대체 | 사용자가 한 번도 안 바꿔도 동작 |

### 대안 비교 (검토 후 위 안 채택)

| 대안 | 장점 | 단점 | 판정 |
|---|---|---|---|
| A. 최초 1회 입력 강제(첫 마을 진입 시 모달) | 익명 닉네임 난립 방지 | 첫 진입에 마찰. v0.3 가설과 무관한 단계 추가 | 기각 — 흐름 차단 |
| **B. 자동 기본명 + 변경 가능 (채택)** | 마찰 0, 원하면 바꿈, 구현 작음 | 안 바꾸면 익명명 다수 | **채택** |
| C. 자동 기본명 고정(변경 불가) | 가장 단순 | "내 이름으로 순위 올리고 싶다"는 경쟁 동기를 못 살림 | 기각 — 가설(경쟁 동기) 약화 |

> plan ↔ 기획서 sync: plan Task 6 Step 3 의 임시 표시명 `"Lord-" + deviceId.Substring(0,4)` 는 본 기획 확정값 `"영주 #" + deviceId.Substring(0,4).ToUpper()` + (있으면)`MetaProfile.DisplayName` 우선 으로 대체. plan 도 동일 시점 delta 로 보강 필요(아래 §7 구현 요청사항에 명시).

## §2. 클라우드 복원 확인 프롬프트

복원은 **로컬 세이브를 서버 데이터로 덮어쓴다.** 되돌릴 수 없으므로 확인 1단계를 둔다 (spec §6 / plan Task 7 Step 6 의 "확인 후 복원" 구체화).

### 확인 다이얼로그

- **사용 컴포넌트**: 공용 2버튼 확인 팝업 `ConfirmPopup` (신규 — §7 에 명세). 복원·충돌 양쪽이 재사용.
- **제목**: `클라우드에서 복원`
- **본문**:
  > 클라우드 저장 데이터로 **현재 진행을 덮어씁니다.**
  > 지금 기기의 진행이 사라질 수 있습니다. 복원할까요?
- **버튼**: 왼쪽 `복원` (강조/확인) · 오른쪽 `취소` (기본/닫기)
  - 버튼 좌우 배치 규칙: 확인 액션을 왼쪽(읽기 흐름상 먼저)·취소를 오른쪽에 둔다. 기존 마을 팝업의 닫기 버튼 위치와 일관.

### 결과 피드백 (토스트, §6 톤 적용)

| 상황 | 토스트 문구 | 비고 |
|---|---|---|
| 복원 성공 | `클라우드에서 복원했습니다.` | 복원 직후 마을 상단바(소울/영주Lv)·열린 팝업 즉시 갱신 |
| 세이브 없음 (서버에 데이터 없음, `GET /save` 404/null) | `클라우드에 저장된 데이터가 없습니다.` | **확인 다이얼로그를 띄우기 전에 먼저 검사한다** — 클라우드에 데이터가 없으면 "덮어쓰기 경고" 다이얼로그를 띄우지 않고 이 토스트만 보여 헛경고를 피한다(§7 구현 노트). 덮어쓰기 미수행 |
| 복원 실패 (통신 실패/타임아웃) | `복원하지 못했습니다. 잠시 후 다시 시도해 주세요.` | 로컬 진행은 그대로 유지 |
| 오프라인 (인증 안 됨, `Cloud == null`) | `오프라인 상태입니다. 클라우드 기능을 사용할 수 없습니다.` | 복원 버튼은 활성이되 누르면 이 토스트 |

## §3. 409 충돌 UX

자동 백업(`PUT /save`) 중 서버가 더 최신(409)일 때. 이 시점 사용자는 백업을 의도한 게 아니라 상점 구매 등 다른 행동을 하던 중이므로 **흐름을 막지 않는다.** 모달을 즉시 띄우지 않고, 다음 두 단계로 처리한다.

### 결정

1. **즉시(자동 백업 도중 충돌)** — 모달 없음. 무음. 마을 "클라우드" 메뉴 버튼에 **알림 점(빨간 dot 배지)** 을 표시해 "확인할 게 있음"을 비차단으로 알린다.
   - 근거: 자동 백업은 fire-and-forget(spec §6). 사용자가 상점에서 구매하는 순간 모달이 튀어나오면 흐름 차단 — §6 원칙 위반.
2. **클라우드 메뉴 진입 시** — 배지가 켜져 있으면 팝업 상단에 충돌 안내 + 복원 권유. `ConfirmPopup` 재사용:
   - **제목**: `더 최신 데이터가 있습니다`
   - **본문**:
     > 다른 기기의 진행이 클라우드에 더 최신으로 저장되어 있습니다.
     > 클라우드 데이터로 복원하면 지금 기기의 진행은 사라질 수 있습니다.
   - **버튼**: 왼쪽 `클라우드로 복원` (확인) · 오른쪽 `나중에` (취소 — 로컬 유지, 배지 유지)
   - `클라우드로 복원` 선택 시 §2 복원 플로우(성공/실패 토스트)로 진입. 성공하면 배지 해제.
   - `나중에` 선택 시 로컬 유지. 배지는 유지(다음 세션 진입에 다시 권유) — 단 같은 세션 내 재팝업 폭주 방지를 위해 충돌 권유는 **세션당 1회만** 노출(세션 플래그 `MetaSession.CloudConflictPromptShownThisSession`, §7 구현 노트).

### 대안 비교

| 대안 | 장점 | 단점 | 판정 |
|---|---|---|---|
| A. 충돌 즉시 모달 | 즉각 인지 | 상점 구매 흐름 차단 — §6 위반 | 기각 |
| **B. 배지 + 메뉴 진입 시 권유 (채택)** | 비차단, 사용자가 원할 때 결정 | 인지 1탭 지연 | **채택** |
| C. 무음 무시(로그만) | 가장 단순 | 충돌 사실을 사용자가 영영 모름 → 기기이전 가치 훼손 | 기각 |

> 배지 신호 출처: plan Task 6 Step 2 `BackupToCloud()` 가 `CloudSaveResult.Conflict` 를 받으면 현재 로그만 남긴다. 본 기획은 여기에 "충돌 플래그 set → 클라우드 메뉴 배지 on" 을 추가 요청(§7). plan delta 보강 대상.

## §4. 리더보드 조회 화면 레이아웃

`LeaderboardPopup` (BuildModalPopup 패턴, plan Task 7). 최단 클리어 경쟁 화면.

### 표시 범위

- **Top N**: **100** (plan 기본값 유지). 풀링 스크롤뷰라 100행 부담 없음.
- **내 순위**: Top 100 안에 들면 해당 행을 **하이라이트**(배경 강조색). Top 100 밖이면 **목록 맨 아래에 구분선 + 내 순위 행 1개** 를 별도로 붙여 항상 "내가 몇 등인지" 보이게 한다 (`GET /leaderboard/me` 결과 — 내 순위 ±주변 행 배열, spec §7).
  - **내 행 판별 기준 (단정)**: displayName 매칭이 아니라 **accountId 매칭**으로 고정한다(중복닉 취약 회피). 비교 대상 accountId 는 `AuthTokenStore` 가 보관한 내 accountId(인증 응답 `{accountId, token}`, spec §5)다. Top 100 목록·`/me` 응답 둘 다 이 accountId 와 일치하는 행을 "내 행"으로 식별한다.
  - 서버 응답 행에 accountId 필드가 없는 경우의 fallback: `/leaderboard/me` 는 내 순위를 중심으로 한 ±주변 배열이므로, 그 배열에서 **내 클리어타임(`MetaProfile.BestClearTime`)과 일치하는 행** 1개를 내 행으로 쓴다(내 기록은 1건뿐이므로 시간 일치로 유일 식별). 이 fallback 도 displayName 에 의존하지 않는다.
  - 내 순위가 비어 있으면(아직 미제출 — `/me` 빈 배열) 하단 고정행 자리에 `아직 기록이 없습니다 — 영웅을 처치하고 순위에 도전하세요.`

### 컬럼 (좌→우)

| 컬럼 | 폭 비율 | 내용 | 정렬 |
|---|---|---|---|
| 순위 | 14% | `1` `2` … (정수). 1~3위는 색 강조(금/은/동 텍스트색) | 중앙 |
| 이름 | 44% | displayName (12자 상한 §1, 넘으면 말줄임 `…`) | 좌 |
| 시간 | 26% | 클리어타임 `m:ss.f` (§ 아래 포맷) | 우 |
| 영웅 | 16% | 영웅 표시명(현재 `Knight` 1종 — 영웅명 텍스트) | 중앙 |

- 폭 비율 합 = 14+44+26+16 = 100%. (셀 실제 px 폭은 LeaderboardPopup 콘텐츠 폭에 비례 — gameplay-programmer 가 프리팹에서 anchor 비율로 배치)
- **헤더 행**: 스크롤 영역 위 고정 1행에 컬럼명 `순위 / 이름 / 시간 / 영웅` (CHText). 스크롤되지 않음.

### 시간 포맷 `m:ss.f`

- 분:초.십분의일초. 예: 92,500 ms → `1:32.5`, 6,000 ms → `0:06.0`, 305,000 ms(5:05) → `5:05.0`.
- 산식 검산: `m = floor(ms/60000)`, `s = (ms - m*60000)/1000` 을 `00.0` 포맷. 예 92500ms → m=1, s=(92500-60000)/1000=32.5 → `1:32.5`. ✓
- plan Task 7 Step 2 `FormatMs` 가 `$"{m}:{s:00.0}"` 로 이미 일치 — 확정.
- 최대값: 전투 5분 제한이므로 클리어타임 ≤ 약 5:00. `m` 1자리로 충분.

| 1위 | 순위 텍스트 금색(#FFD24A) |

| 3위 | 순위 텍스트 동색(#D08B5B) |

| 하단 고정 내 순위 행(Top100 밖) | 위 배경 강조 + 구분선 위 배치 |

## §6. 오프라인 / 실패 피드백 톤

spec §8 원칙: 서버 불통/타임아웃 → 조용히 로컬 유지, 게임 흐름 차단 금지, 사용자엔 가벼운 안내(토스트/로그).

### 결정 — 안내 수위 매트릭스

피드백은 **"사용자가 방금 직접 누른 행동인가"** 로 갈린다. 직접 행동의 실패는 토스트로 알리고, 백그라운드 자동 동작의 실패는 무음 로그만.

| 동작 | 트리거 | 실패 시 | 근거 |
|---|---|---|---|
| 마을 진입 자동 인증 | 마을 로드(자동) | **무음 로그만**. 클라우드 메뉴 상태가 `오프라인` 으로 표시될 뿐 | 사용자가 누른 게 아님 — 토스트 띄우면 매 진입 성가심 |
| 자동 백업(`PUT /save`) | 로컬 저장마다(자동) | **무음 로그만**. 단 409 충돌은 §3 배지 | 상점 구매 흐름 차단 금지 |
| 리더보드 자동 제출 | 승리 직후(자동) | **무음 로그만**. 결과 화면에 별도 실패 표기 없음 | 승리의 쾌감 흐름 보호 — 제출 실패로 결과창에 빨간 글씨 띄우지 않음 |
| 클라우드 복원 | 사용자가 `복원` 버튼 클릭 | **토스트** (§2 성공/실패/없음/오프라인 문구) | 직접 행동 → 결과 피드백 필수 |
| 표시명 변경 | 사용자가 `변경` 확인 클릭 | 성공 토스트 `표시명을 변경했습니다.` / 빈값 토스트 `표시명을 입력해 주세요.` | 직접 행동 |
| 순위표 열기 | 사용자가 `순위표` 클릭 | 팝업 내 `_emptyText` 안내(§4) — 토스트 아님 | 화면 자체가 결과를 보여줌 |

### 토스트 컴포넌트

- ChvjPackage·게임 코드에 토스트 없음 → **신규 공용 토스트** `ToastView` (게임 측, §7). 화면 하단 중앙, 1.8초 노출 후 페이드 아웃, 자동 닫힘. 동시 1개(연속 호출 시 최신 메시지로 교체).
- 토스트는 입력을 막지 않는다(클릭 통과). 게임 흐름 차단 금지 원칙 준수.

### 대안 비교 (자동 동작 실패 안내)

| 대안 | 장점 | 단점 | 판정 |
|---|---|---|---|
| A. 모든 실패를 토스트 | 투명성 | 인증/백업 실패가 매번 떠 성가심, 오프라인 플레이 짜증 | 기각 |
| **B. 직접 행동만 토스트, 자동은 무음 로그 (채택)** | 흐름 보호 + 필요한 피드백만 | 자동 백업 실패를 사용자가 모름 | **채택** (백업 실패는 다음 저장 때 재시도되므로 무음 허용) |
| C. 전부 무음 | 가장 조용 | 복원 눌렀는데 아무 반응 없음 → 고장처럼 느낌 | 기각 |

**충돌 권유 재팝업 세션 플래그 (§3 — 메뉴 진입당 1회)**:
- `CloudPopup` 진입 시 `CloudConflictPending == true` 면 충돌 권유 영역(§3)을 1회 표시하고, 같은 세션 내 재진입 폭주를 막기 위해 **세션 플래그 `MetaSession.CloudConflictPromptShownThisSession`(static bool)** 으로 가드한다.
- 동작: `CloudPopup` 열릴 때 플래그가 false 이고 `CloudConflictPending` 이 true 면 권유 표시 + 플래그 true 로 set. 같은 세션 재진입 시 권유 재팝업 안 함(배지 dot 은 그대로 유지). `나중에` 선택 시에도 배지는 유지(다음 세션 진입에 다시 권유). 복원 성공 시 `CloudConflictPending=false` + 플래그 무관.

**ConfirmPopup 인자** (UIArg, Rule 03 §5 — 같은 파일 상단):
```
public class ConfirmPopupArg : UIArg
{
    public string Title;
    public string Message;
    public string ConfirmLabel;   //# 예: "복원"
    public string CancelLabel;    //# 예: "취소"
    public Action OnConfirm;
    public Action OnCancel;       //# null 허용
}
```

**ToastView 호출** — 정적 헬퍼 1개 권장(예: `ToastView.Show(string message)`), 내부에서 `CHMUI.Instance.ShowUI(EUI.ToastView, ...)`. 동시 1개·1.8초·페이드아웃·입력통과.

## §8. 확정 사실 / 구현 주의 (디자인 결정 아님)

서버 계약에 의존하는 항목으로, 본 기획은 spec 의 확정 사실에 맞춰 단정한다.

1. **표시명은 클라우드 동기 대상 아님 (확정 — §1·§7)**: 서버 `MetaProfileDto` 에 displayName 필드가 없으므로(spec §4 필드 목록) 표시명은 로컬 보관 + 리더보드 제출 시에만 동봉된다. 기기 복원으로 표시명은 돌아오지 않고 새 기기는 기본명으로 시작한다. (이전 "양 경로 중 택1" 서술은 spec §4 확정 사실로 한 갈래로 단정 — 더 이상 미해결 아님.)
2. **`GET /leaderboard/me` 는 내 순위 ±주변 행 배열 (spec §7 확정)** — 단일 객체가 아니라 `List<LeaderboardRowDto>` 다. §4 의 "하단 고정 내 순위 행" 판별은 **displayName 매칭이 아니라 내 식별 필드(accountId, `AuthTokenStore` 가 보관)** 기준으로 고정한다(중복닉 취약 회피). 서버 응답 행에 accountId 가 없거나 '나' 표시가 없으면, `GET /leaderboard/me` 응답 중 **내 순위에 해당하는 행(서버가 ±주변의 중심으로 반환하는 내 행)** 1개를 하단 고정행에 쓴다. 식별 방법 단정은 §4 참조.
