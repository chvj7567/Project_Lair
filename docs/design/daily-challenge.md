## § 헤더

- **목표**: 날짜(한국 시간) 하나가 정하는 **영웅 1명 + 규칙 2개 + 오늘의 유물 2개 + 카드 시드** 조합을 모든 플레이어가 똑같이 받아 하루 3번 도전하고, 가장 좋은 기록을 그날의 데일리 순위에 올리는 일일 도전 모드를 마을 팝업 하나로 만든다.
- **검증 가설**: (1) "어제와 다른 판" 이 매일 열리는 것이 고정 챕터(1-1~5-5)만 있을 때의 "같은 판 반복" 피로를 줄이고 **재방문**(일일 접속률·연속 일수)을 올리는가. (2) 모두가 같은 조합을 받는 하루짜리 순위가 기존 스테이지 최단 랭킹보다 **경쟁 동기**(순위 조회·재도전 횟수)를 더 만드는가. (3) 신규 몬스터·신규 규칙 없이 기존 영웅 5종 × 규칙 프리셋 28행 × 유물 11종 재조합만으로 날마다 다른 판이라는 체감이 생기는가(조합 편차 게이트 DQ3).
- **현재 단계 범위 적합성**: **범위 밖이었던 항목의 명시 승격 요청 - 사용자 승인 필요.** CLAUDE.md §8 은 "데일리" 를 개별 승격 전까지 금지한다(챕터·난이도·유물 3개 항목 문구). §14 에 승격 문구 초안이 있으며 **승인 전에는 구현에 착수하지 않는다.** 신규 몬스터·신규 스테이지 규칙·★ 목표는 쓰지 않는다. 서버는 Firebase 클라이언트 코드 범위 유지 - Firestore 보안 규칙·복합 인덱스는 **콘솔 의존성**으로만 명시한다(§6.4, 이 레포에서 작성하지 않음). 별도 메인 메뉴 금지 유지(진입은 마을 HUD 타일 → 팝업).
- **핵심 메커니즘**: (a) `dayIndex = floor((서버 UTC ms + 9시간) / 1일)` 을 키로 결정적 난수(SplitMix64)를 굴려 조합을 만든다. 서버 시각은 강제 갱신한 Firebase ID 토큰의 `iat` 로 얻고, 세션 안에서는 기기 시계 대신 단조 시계로 전진시킨다. (b) 전투는 `SelectedStage` 를 건드리지 않는 **세션 전용 데일리 전투 컨텍스트**로 돌며, 끝나도 챕터 진행·스테이지 기록·스테이지 랭킹을 바꾸지 않는다. (c) 점수 = 승리면 클리어 시간(ms), 패배면 `300000 + 남은 영웅 HP 천분율` 인 오름차순 정수 하나 - 모든 참가자가 순위를 갖는다. 첫 승리에 소울 보너스(연속 일수 배율)와 유물 1개 확정 굴림.

**해석 확인**: 요청의 "챕터 스테이지는 고정, 데일리는 날짜 시드로 모두에게 같은 조합, 하루 1판~N회" 를 **하루 3회 도전 · 최고 기록 1건 순위 반영** 으로 좁혔다(§1.4 대안 비교). "기존 자산 최대 재사용" 에 맞춰 신규 콘텐츠 데이터는 설정 JSON 1개(`DailyConfig`)뿐이고 규칙·유물·영웅·카드 풀은 기존 데이터에서 도출한다.

## 1. 핵심 루프 · 동기

### 1.1 루프

```
마을 진입 → HUD "데일리" 타일(새 날이면 금색 테두리) → 데일리 팝업
  → 오늘의 영웅·규칙·유물·순위·내 남은 도전 확인
  → [도전 시작] (도전 1회 차감) → 전투 (평소 5분 자동전투 + 카드 선택)
  → 결과창: 점수 · 오늘의 순위 · (첫 승리면) 보너스 소울 + 확정 유물
  → [다시 도전 (남은 n)] 으로 즉시 재도전 / [마을로]
  → 다음 날 0시(한국 시간) 새 조합
```

### 1.2 동기 설계

| 동기 | 장치 | 근거 |
|---|---|---|
| 재방문 (매일) | 날짜마다 바뀌는 조합 + 첫 승리 보너스(소울 + 유물 확정) + 연속 일수 배율 | 유물은 수집 노력이 큰 자산(52 슬롯, `relics.md` §2.3) - "하루 1개 확정" 이 명확한 일일 보상이 된다 |
| 경쟁 | 같은 조합·같은 카드 시드 → 실력·빌드 판단이 순위를 가른다. 패배도 순위에 오른다 | 기존 스테이지 랭킹은 상점·유물 차이로 조합이 다르다. 데일리는 전투 효과 유물을 끄고 공통 유물을 줘서 차이를 줄인다(§3) |
| 학습 | 하루 3회, 같은 카드 시드 → 첫 도전에서 본 제시 카드를 두 번째 도전에서 다르게 고를 수 있다 | 같은 퍼즐을 다시 푸는 재미. 3회 상한이 무한 시드 파밍을 막는다 |
| 콘텐츠 예고 | 아직 도달하지 못한 챕터의 영웅(예: 성기사)도 데일리에 나온다 | 해금 조건이 1-5 클리어라 신규 유저도 후반 영웅을 미리 맛본다(§1.3) |

### 1.3 해금

- 조건: `ClearedStage >= DailyConfig.unlockClearedStage`(초기값 **5** = 1-5 클리어). 근거: 카드·스포너·영웅 HP 구간의 기본 루프를 한 챕터 동안 배운 뒤 연다. 데일리 영웅은 챕터 2~5 영웅도 나오지만 `x-2` 스테이지 기준 배율(§2.4)이라 최악 조합도 기준 메타에서 236.3초로 300초 천장 안이다(§2.7 검산).
- 미해금 상태: 타일은 보이되 자물쇠 표시, 누르면 토스트 `1-5 클리어 시 해금`(기존 `{0} 클리어 시 해금` 문구 재사용, 인자 "1-5"). 팝업은 열지 않는다.

### 1.4 시도 횟수 - 대안 비교

| 안 | 내용 | trade-off | 판정 |
|---|---|---|---|
| A. 하루 1회 | 진짜 "한 판" | 첫 시도의 실수 한 번이 하루를 망친다. 카드 시드 학습 재미가 없다 | 기각 |
| **B. 하루 3회, 최고 기록 반영 (권장)** | 시작 시 차감, 최고 점수 1건만 순위 | 실수 복구와 개선 동기 둘 다. 3판 x 5분 = 하루 최대 15분 - 세션 길이 부담이 작다 | **채택** |
| C. 무제한, 최고 기록 반영 | | 시간 많은 플레이어가 순위를 독식(시드 학습 반복). 보상은 1회라 경제는 안전하나 순위 의미가 약해진다 | 기각 |

- **차감 시점 = 전투 시작**(데일리 전투 컨텍스트로 영웅을 스폰하는 순간). 전투 중 뒤로가기 종료도 1회 소모. 근거: "카드가 나쁘면 나가서 다시" 를 막는다(카드 시드가 고정이라 같은 카드가 다시 나오지만, 판 초반 상황 리셋은 막아야 공정하다).
- 수치: `DailyConfig.attemptsPerDay = 3` (JSON 튜닝).

## 2. 조합 생성 (시드 규칙)

### 2.1 날짜 경계 - 대안 비교

| 안 | 내용 | trade-off | 판정 |
|---|---|---|---|
| A. UTC 0시 | 전 세계 동일 | 한국 시간 오전 9시 갱신 - 한국어 전용 게임(`Strings_Ko` 단일)의 출근·등교 시간과 겹쳐 첫 접속이 어색하다 | 기각 |
| **B. 한국 시간(UTC+9) 0시 고정 (권장)** | `utcOffsetMinutes = 540` 고정, 기기 지역 무관 | 모든 플레이어가 같은 순간 같은 날짜 → 순위 공정. 해외 체류 유저는 현지 시각 기준 갱신 시각이 달라진다(알려진 제약) | **채택** |
| C. 기기 지역 시간 0시 | 각자 현지 자정 | 같은 순간에 날짜가 다른 플레이어가 생겨 "같은 날 같은 조합" 이 깨지고 순위 문서 키가 갈린다 | 기각 |

- 산식: `dayIndex = floor((serverUtcMs + utcOffsetMinutes x 60000) / 86400000)` (정수, 1970-01-01 한국 날짜 = 0).
- 검산: 2026-10-27(한국) 0시 = `2026-10-26T15:00:00Z` = 유닉스 1,793,026,800초. (1,793,026,800 + 32,400) / 86,400 = 20,753.000 → `dayIndex 20753`. 1초 전(`14:59:59Z`)은 20,752.9999 → 20752. 2026-01-01 = 20454(1970~2025 = 56년 x 365 + 윤년 14 = 20,454), 10월 27일은 그 해 299일째(1~9월 273일 + 26) → 20454 + 299 = 20753 일치.

### 2.2 서버 시간 - 기기 시계 조작 대응

**대안 비교**

| 안 | 내용 | trade-off | 판정 |
|---|---|---|---|
| A. 기기 시계만 | 구현 0 | 시계를 내일로 돌려 내일 조합 연습, 어제로 돌려 도전 횟수 재획득 가능 | 기각 |
| **B. Firebase ID 토큰 `iat` (권장)** | `TokenAsync(forceRefresh: true)` 로 받은 JWT 페이로드의 `iat`(발급 시각, 초) = 서버 현재 시각 | 보안 규칙 변경 없음, 새 컬렉션 없음. 정밀도 1초(0시 경계 판정 오차 ±1초). 온라인 필요 | **채택** |
| C. Firestore `ServerTimestamp` 기록 후 재조회 | 전용 문서에 쓰고 읽기 | 전용 컬렉션 + 보안 규칙 추가가 필요. **`saves/{uid}` 를 시계 탐침으로 쓰면 `serverVersion` 이 바뀌어 클라우드 충돌 판정 기준선이 깨진다 - 절대 금지** | 기각 (B 실패 시 후속 대안) |

**동작 명세**

1. 데일리 팝업을 열 때마다 서버 시각을 1회 받는다: `serverUtcMsAtFetch = iat x 1000`, 동시에 `realtimeAtFetch = Time.realtimeSinceStartupAsDouble`.
2. 이후 같은 세션의 "지금" = `serverUtcMsAtFetch + (realtime - realtimeAtFetch) x 1000`. **기기 시계(`DateTime.Now`)는 쓰지 않는다** - 세션 중 기기 시계를 바꿔도 날짜가 움직이지 않는다.
3. 도전 시작 버튼을 누르는 순간 2의 값으로 `dayIndex` 를 다시 계산한다. 팝업을 연 뒤 0시를 넘겼으면 조합을 새 날로 갱신하고 토스트 `날짜가 바뀌었습니다. 새 도전이 열렸습니다` 를 띄우며 시작은 하지 않는다(새 조합을 보고 다시 누르게).
4. 서버 시각을 얻지 못하면(오프라인·인증 실패) 데일리는 **시작 불가**(§8 오프라인).
5. 서버 측 최종 방어는 순위 문서 쓰기 보안 규칙이 `request.time` 으로 날짜를 검사하는 것이다(§6.4 의존성 C-2). 클라이언트 방어(1~4)를 우회해도 다른 날짜 문서는 서버가 거부한다.

### 2.3 결정적 난수와 뽑기 순서

- **생성기**: SplitMix64(64비트, 상수 `0x9E3779B97F4A7C15` 가산, 믹스 `x ^= x >> 30; x *= 0xBF58476D1CE4E5B9; x ^= x >> 27; x *= 0x94D049BB133111EB; x ^= x >> 31`). `System.Random`·`UnityEngine.Random` 은 조합 생성에 쓰지 않는다(런타임·버전 간 동일성을 이 레포가 통제할 수 없음). 순수 C# 정적 유틸, Unity 비의존.
- **정수 뽑기**: `NextInt(n) = (int)(Next() % (ulong)n)` (n <= 28 이라 모듈로 편향은 2^64 대비 무시 가능 - 최대 편향 28 / 2^64).
- **시드**: `daySeed = Mix(DailySalt ^ (ulong)dayIndex)`, `DailySalt` 는 코드 상수(출시 후 변경 금지 - 바꾸면 그날 순위가 클라이언트 버전마다 갈린다). 무한 탑과 생성기 공유 시 탑은 다른 salt 를 쓴다(§10 연동 가정 L-2).
- **고정 뽑기 순서** (순서가 바뀌면 같은 날 조합이 바뀐다 - 테스트로 고정, §11):

| 순번 | 뽑기 | 입력 풀 | 비고 |
|---|---|---|---|
| 0 | 영웅 | 5일 블록 순열(§2.4) | `daySeed` 가 아니라 블록 시드 사용 |
| 1 | 상시 규칙 프리셋 | 상시 풀 19행(§2.5) | |
| 2 | 페이즈 규칙 프리셋 | 페이즈 풀 9행에서 충돌 제외(§2.5) | |
| 3 | 오늘의 유물 A (일반) | 일반·능력치/전투 효과 5종 | |
| 4 | 오늘의 유물 B (희귀·전설) | 희귀·전설·능력치/전투 효과 6종 | |
| 5 | 패시브 카드 덱 시드 | `(int)(Next() & 0x7FFFFFFF)`, 0 이면 1 | `CardDeck(seed)` 는 0 을 "무작위" 로 해석하므로 0 금지 |
| 6 | 액티브 카드 덱 시드 | 같음 | |

### 2.4 영웅 - 5일 블록 순열

- **대안 비교**: (A) 매일 균등 추첨 - 같은 영웅 2~3일 연속이 생긴다(연속 확률 1/5). (B) "어제와 다르게" 재추첨 - 어제를 알려면 그제가 필요한 재귀가 생긴다. **(C) 5일 블록 순열 (권장)** - `block = floor(dayIndex / 5)`, 블록 시드 `Mix(DailySalt ^ 0xB10C ^ block)` 로 5명 Fisher-Yates 셔플, `hero = perm[dayIndex mod 5]`. 5일마다 5명이 정확히 한 번씩 나온다. 블록 경계 연속 방지: 블록 k+1 의 `perm[0]` 이 블록 k 의 `perm[4]` 와 같으면 k+1 의 `perm[0]` 과 `perm[1]` 을 맞바꾼다(직전 블록 1개만 계산, 재귀 없음).
- 영웅 풀 = `Chapter.json` 의 `heroId` 를 `chapterId` 오름차순으로 정렬한 5명(Knight, Archer, Assassin, Berserker, Paladin). 파일 행 순서가 아니라 키 정렬이 기준이다.
- **기준 스테이지** = (그 영웅의 챕터, `DailyConfig.baseStageIndex` = **2**). 영웅 HP·공격력 배율·배경·영웅 외형(`HeroStageVariantConfig`)을 이 스테이지에서 가져온다. **그 스테이지의 원래 규칙(`Stage_Rule`)은 쓰지 않고** 데일리 규칙 2개로 대체한다.
- 예: 2026-10-27 은 `dayIndex 20753`, `block 4150`, 블록 내 위치 3. 실제 영웅은 셔플 결과에 따른다(§11 골든 벡터에서 고정).

### 2.5 규칙 - 기존 `Stage_Rule` 행을 프리셋으로 재사용

- **프리셋** = 기존 `Stage_Rule` 행 하나(`chapterId, stageIndex, ruleIndex`)에 딸린 `Stage_Rule_Param` 전부 + `Stage_Rule_Trigger`(있으면). 데일리는 이 키를 참조만 하므로 **신규 규칙·신규 수치가 0** 이다.
- **풀 분류**(트리거 행 유무로 자동 분류, 키 `(chapterId, stageIndex, ruleIndex)` 오름차순 정렬):

| 풀 | 행 수 | 구성 (현행 데이터) |
|---|---|---|
| 상시 | **19** | HolySpring 5 (1-2, 2-4#1, 3-3, 4-3, 5-4#1) · DenseFog 6 (1-3, 2-3, 2-4#2, 3-4#2, 4-4#2, 5-3) · SealedNest 8 (1-4, 2-2, 3-2, 3-4#1, 4-2, 4-4#1, 5-2, 5-4#2) |
| 페이즈 | **9** | BossBulwark 4 (1-5 0.55, 3-5#1 0.75, 4-5#1 0.55, 5-5#2 0.35) · ArrowRain 2 (2-5#1 0.75, 4-5#2 0.35) · HunterTraps 3 (2-5#2 0.35, 3-5#2 0.35, 5-5#1 0.75) |

검산: 상시 5 + 6 + 8 = 19, 페이즈 4 + 2 + 3 = 9, 합 28 = `Stage_Rule.json` 행 수 28.

- **조합 규칙**: 상시 1개 + 페이즈 1개 = 하루 규칙 2개 고정.
  - 같은 `ruleId` 중복: 두 풀의 `ruleId` 집합이 서로소라 구조적으로 불가.
  - **HP 임계 충돌 방지**(`chapter-system.md` §3.2): 상시 프리셋이 SealedNest 이고 그 `unlockHpFraction` 이 페이즈 프리셋의 트리거 `hpFraction` 과 같으면 그 페이즈 프리셋을 후보에서 뺀 뒤 뽑는다. 현행 데이터에서 해당 쌍은 5-4#2 SealedNest(0.55) ↔ 1-5 / 4-5#1 BossBulwark(0.55) 뿐이며, 이때 페이즈 후보는 9 - 2 = 7행.
  - 트리거 값은 원본 그대로(0.35 / 0.55 / 0.75)라 패시브 임계(0.9~0.1)·스킬 게이트(0.85/0.65/0.45)와 이미 어긋나 있다.
- **풀 정의 - 대안**: (A) **`Stage_Rule` 에서 자동 도출 (권장, YAGNI)** - 데이터 추가 0, 신규 스테이지 규칙 행이 생기면 자동으로 데일리 풀에 들어간다. (B) 별도 `Daily_RulePool` JSON 으로 큐레이션 - 특정 프리셋 제외·가중치가 가능하나 지금은 제외할 근거 데이터가 없다. QA 에서 특정 프리셋 조합이 게이트 DQ3(조합 편차)을 깨면 그때 B 를 도입한다.
- **데이터 변경 주의**: `Stage_Rule` 행을 추가·삭제하면 풀 인덱스가 바뀌어 같은 날 조합이 클라이언트 버전마다 달라진다. 규칙 데이터 변경은 배포 공지 날의 0시 이후 적용을 전제로 한다(위험 R-4).

### 2.6 조건 - 오늘의 유물 2개 + 난이도

- **오늘의 유물**(`relics.md` 의 유물 효과를 그대로 재사용, 이 판에만 적용):
  - A: `Relic.json` 에서 `rarity = Common` 이고 `category` 가 `Stat`·`Combat` 인 5종(HeartOfStone, RustyBlade, SwiftBoots, EmberBrand, AmbushHorn) 중 1개, 중첩 `DailyConfig.commonRelicStack` = **3**.
  - B: `rarity` 가 `Rare`·`Legendary` 이고 `category` 가 `Stat`·`Combat` 인 6종(BrokenHourglass, BreedingCharm, KingsCrownShard, ThunderShard, CursedBanner, WrathSpirit) 중 1개, 중첩 `DailyConfig.rareRelicStack` = **1**.
  - 편의(`Convenience`) 유물은 뽑지 않는다(보상·배속은 순위와 무관한 축이라 "조건" 이 되지 못함).
  - 중첩이 그 유물의 `maxStack` 을 넘으면 `maxStack` 으로 클램프(현행 A 후보 최소 maxStack 3, B 후보 최소 1 이라 초기값에서는 클램프 없음).
  - 풀 정렬 기준 = `relicId` 문자열 오름차순(서수 비교).
- **난이도**: `DailyConfig.difficulty` = **1 (Normal)** 고정. `DifficultyTable` 의 Normal 행(HP x1.15, 공격력 x1.10)을 그대로 쓴다. 근거: 기준 스테이지가 `x-2`(챕터 중반 이전)라 Easy 면 상점 진행이 높은 유저에게 너무 짧다(§2.7 표의 최소 165초). 날짜별 난이도 변동은 하지 않는다(날마다 바뀌는 조건은 오늘의 유물 2개 + 규칙 2개가 맡는다 - YAGNI).
- **카드 시드**: 순번 5·6 의 시드로 패시브·액티브 덱을 만든다(`CardDeck` 이 이미 시드 인자를 받는다). 같은 날 같은 선택을 하면 같은 카드가 제시된다. 선택이 다르면 3픽 상한 제외가 달라져 이후 제시가 달라지는 것은 정상이다.

### 2.7 시간 예산 점검 (`difficulty-select.md` §1.3 방식)

기대 처치 시간 ≈ `targetClearSec(x-2) x 1.15(Normal) x RF_daily ÷ RF_base` (기준 메타 `M_ref` 대비, 오늘의 유물 효과 미반영 = 보수적).

- `RF_base` = 기준 스테이지 원래 규칙의 환산 계수(배율이 이것으로 나눠져 있으므로 원래 규칙을 빼면 되돌린다): 1-2 HolySpring 1.077 / 2-2 SealedNest(Phantom 0.70) 1.040 / 3-2 SealedNest(Plague 0.60) = 1 ÷ (1 - 0.061 x 0.40) = 1.025 / 4-2 SealedNest(Wisp 0.60) = 1 ÷ (1 - 0.170 x 0.40) = 1.073 / 5-2 SealedNest(Hex 0.60) = 1 ÷ (1 - 0.183 x 0.40) = 1.079.
- `RF_daily` 범위: 최소 = DenseFog 1.000 x BossBulwark 1.030 = **1.030**. 최대 = SealedNest(Hex 0.50 · Reaper 0.70) 1 ÷ (1 - 0.183 x 0.50) = 1.101 x 페이즈 최대 1.060(ArrowRain·HunterTraps 각 6% 추정, `chapter-system.md` §4.1) = **1.167**.

| 영웅 (기준 스테이지, target) | RF_base | 최소 (RF 1.030) | 최대 (RF 1.167) | 300초 대비 최대 여유 |
|---|---|---|---|---|
| 기사 (1-2, 150) | 1.077 | 165.0 | 186.9 | 113.1초 |
| 궁수 (2-2, 175) | 1.040 | 199.3 | 225.8 | 74.2초 |
| 암살자 (3-2, 180) | 1.025 | 208.0 | 235.7 | 64.3초 |
| 광전사 (4-2, 185) | 1.073 | 204.2 | 231.4 | 68.6초 |
| 성기사 (5-2, 190) | 1.079 | 208.6 | 236.3 | 63.7초 |

검산: 150 x 1.15 = 172.5, x1.030 = 177.7, ÷1.077 = 165.0 / 172.5 x 1.167 = 201.3, ÷1.077 = 186.9. 175 x 1.15 = 201.25, x1.167 = 234.9, ÷1.040 = 225.8. 180 x 1.15 = 207.0, x1.167 = 241.6, ÷1.025 = 235.7. 185 x 1.15 = 212.75, x1.167 = 248.3, ÷1.073 = 231.4. 190 x 1.15 = 218.5, x1.167 = 255.0, ÷1.079 = 236.3 / x1.030 = 225.1, ÷1.079 = 208.6.

- 판정: 최악 조합도 기준 메타에서 63.7초 여유. 오늘의 유물은 몬스터를 강하게 하므로 실제 시간은 더 짧다. 남은 위험은 **해금 직후 유저(1-5 막 클리어, 상점 진행 낮음)가 성기사·암살자 데일리를 받을 때** - `M_ref` 보다 메타가 낮으면 시간이 `M_ref ÷ M` 배 늘어난다. 게이트 DQ2 로 판정하고 레버는 `baseStageIndex`(2 → 1)와 `difficulty`(1 → 0) 숫자뿐이다.

## 4. 데이터 구조표 (사용자 승인 게이트 - 필수 확인)

> Rule 02 §11-1 적용. 콘텐츠·밸런스 = JSON(`Assets/_Lair/Data/Json/`, 파일명 = `EData` 값명). 세이브 = `MetaProfile` 엔트리 리스트(`DifficultyClearEntry`/`RelicEntry` 선례). sentinel(-1/0/null) 미사용 - "그날 기록 없음" 은 행이 없는 것으로 표현한다.

### 4.1 엔티티 / 관계 트리

```

[도출 - 저장하지 않음, 매일 계산]
DailyChallenge (런타임 값 객체)  "dayIndex 하루의 조합"

 |-- heroId ─────────────────► HeroArchetype.heroId (= Chapter.heroId)
 |-- baseStage ──────────────► Stage (chapterId = 영웅 챕터, stageIndex = DailyConfig.baseStageIndex)
 |-- alwaysRule ─────────────► Stage_Rule (chapterId, stageIndex, ruleIndex)  + Param + (Trigger 없음)
 |-- phaseRule ──────────────► Stage_Rule (chapterId, stageIndex, ruleIndex)  + Param + Trigger

 |-- difficulty ─────────────► Difficulty.difficulty (= DailyConfig.difficulty)

MetaProfile (세이브 루트)
 |-- DailyDays    : List<DailyDayEntry>    { Day (PK), AttemptsUsed (>=1) }   <- 그날 도전을 1회라도 시작한 날만

[원격 - Firestore, 이 레포는 클라이언트만]
dailyLeaderboard/{day}_{uid}  { uid, day, displayName, hero, score, comboKey, updatedAt }
```

### 4.3 파생 규칙 (조회 헬퍼 - 의도만, 시그니처는 gameplay-programmer 판단)

- `AttemptsLeft(day) = Max(0, attemptsPerDay - (DailyDays 에 day 행이 있으면 AttemptsUsed, 없으면 0))`
- `IsWinScore(score) = score <= 300000`, `HasWonOn(day) = DailyResults 의 day 행이 있고 IsWinScore(BestScore)`
- `DisplayStreak(today) = (DailyResults 에 today 행 존재 || today - 1 행 존재) ? DailyStreak : 0` (어제·오늘 모두 끝낸 판이 없으면 끊긴 연속이라 0 표시. 저장값은 다음 갱신 때 덮인다)
- **보관 정리**: 데일리 판이 끝나 저장할 때 `Day < today - 6` 인 행을 두 리스트에서 지운다(최근 7일만 유지 - 연속 판정에는 어제 행 하나만 필요, 7일은 팝업 출석 칸 표시용).

## 5. 저장 · 마이그레이션 · 클라우드

### 5.1 `MetaProfile` Version 10 → 11 (기획 초안 8 → 9, L-1 확정)

| 단계 | 규칙 (`MetaProfileMigration.Apply`, 멱등) |
|---|---|
| 1 | `CurrentVersion = 11`. `Version < 11` 이면 11 로 승격 (이후 육성 재화 분리가 12 로 다시 올림) |
| 2 | 기존 단계(난이도·유물 포함) 유지 |
| 3 | `DailyDays` / `DailyResults` null 이면 빈 리스트 |
| 4 | `DailyDays` 정리: null 행, `Day < 0`, `AttemptsUsed < 1` 제거. 같은 `Day` 중복이면 `AttemptsUsed` 최댓값 한 행 |
| 5 | `DailyResults` 정리: null 행, `Day < 0`, `BestScore < 1`, `BestScore > 301000` 제거. 같은 `Day` 중복이면 `BestScore` 최솟값 한 행 |
| 6 | `DailyStreak < 0` 이면 0 |

- `AttemptsUsed > attemptsPerDay` 클램프는 마이그레이션에서 하지 않는다(설정 JSON 로드 전일 수 있음 - `difficulty-select.md` §3.1 선례). `AttemptsLeft` 의 `Max(0, …)` 가 읽기 시점에 방어한다.
- v10 이하 세이브: 필드 부재 → 빈 리스트 / 0.

### 5.2 클라우드 동기 - 도전 횟수 환불 방지

- `CopyFrom` 은 다른 필드와 같은 규약(전체 대체)으로 세 필드를 복사한다.
- **복원 직후 병합**: 클라우드 복원(`CopyFrom` + `Migration.Apply`) 직후, 복원 **전** 로컬 값과 날짜별로 합친다 - `DailyDays` 는 같은 `Day` 의 `AttemptsUsed` 최댓값, `DailyResults` 는 같은 `Day` 의 `BestScore` 최솟값, 한쪽에만 있는 행은 유지, `DailyStreak` 는 최댓값. 이유: 오래된 클라우드 세이브를 복원해 오늘 쓴 도전 횟수를 되돌리는 것을 막는다. 이 병합은 데일리 세 필드에만 적용한다(다른 필드의 전체 대체 규칙은 그대로).
- 업로드 `schemaVersion` 은 `profile.Version` 그대로(자동 - 데일리 도입 시 11, 현행 12). 충돌 판정(`serverVersion` 타임스탬프)·충돌 UX 변경 없음.
- 구버전(v10) 클라이언트가 v11 문서를 복원하면 데일리 필드를 무시하고 이후 업로드에서 지운다(유물 선례와 같은 알려진 제약, 신구 클라이언트 동시 배포 전제).
- **알려진 한계**: 재설치·새 기기 = 새 익명 uid = 데일리 도전 횟수가 새로 3회(로컬·클라우드 둘 다 새 계정). 순위 문서도 uid 단위라 한 사람이 두 줄로 오를 수 있다. 구글 로그인(Spec 2) 전까지 감수한다.

## 6. 데일리 리더보드 (클라이언트)

### 6.1 점수 인코딩 - 대안 비교

| 안 | 내용 | trade-off | 판정 |
|---|---|---|---|
| A. 승리만 순위 (클리어 시간) | 기존 스테이지 랭킹과 동일 | 그날 못 이긴 플레이어는 순위가 없어 경쟁에서 빠진다 | 기각 |
| **B. 단일 오름차순 정수 (권장)** | 승리 = `clearTimeMs`(1~300000), 패배 = `300000 + 남은 영웅 HP 천분율`(1~1000 → 300001~301000) | 모든 참가자가 순위를 갖고, 승리가 항상 패배보다 위. 정렬 필드 하나라 기존 "Top N 오름차순 + 내 순위 = 나보다 작은 값 개수 + 1" 읽기 방식을 그대로 쓴다 | **채택** |
| C. 승리/패배 두 필드 복합 정렬 | | 복합 인덱스 추가, 읽기 쿼리 신설 | 기각 |

- 남은 HP 천분율 = `ceil(영웅 남은 HP ÷ 영웅 최대 HP x 1000)`, 1~1000 클램프. 올림인 이유: 패배인데 0 이 나오면 승리(300000)와 겹친다.
- 검산: 2분 51.3초 승리 = 171,300. 패배·영웅 HP 12.0% 남음 = 300,000 + 120 = 300,120. 무피해 패배 = 301,000(최하위).
- 표시: 승리 `2:51.3`(기존 랭킹 시간 포맷), 패배 `패배 · 영웅 HP 12% 남음`(천분율 ÷ 10 반올림 정수 %).
- 동점: 같은 점수는 같은 순위 번호로 표시한다(내 순위 = 나보다 작은 점수 수 + 1 규칙이 자연히 이렇게 계산된다). Top 목록의 동점 행 순서는 정렬 결과 그대로.

### 6.2 제출 규칙

- 데일리 판이 끝날 때마다(승패 무관) 그날의 **로컬 최고 점수**(`DailyResults` 의 그날 행)를 제출한다. 서버에 이미 더 좋은(작은) 점수가 있으면 쓰지 않는다(`StageLeaderboard.ShouldReplace` 와 같은 규칙, 동점 미갱신).
- 제출 실패(오프라인 등): 토스트 `기록 제출 실패 - 다음 도전 때 다시 제출됩니다`. 별도 재시도 큐 없음 - 다음 판 종료 시 로컬 최고를 다시 제출하므로 자연 재시도된다. 그날 마지막 판에서 실패하면 그 기록은 순위에 오르지 않는다(위험 R-6).
- 판 도중 0시를 넘긴 판은 **시작한 날짜**로 기록·제출한다(데일리 전투 컨텍스트에 `dayIndex` 를 시작 시 확정). 보안 규칙의 하루 유예(§6.4 C-2)가 이를 허용한다.
- 데일리 판은 기존 `SubmitScoreAsync`(전역)·`SubmitStageScoreAsync`(스테이지)를 **호출하지 않는다**.

## 7. 보상 · 연속 일수

### 7.1 보상 표

| 상황 | 소울·XP | 데일리 보너스 | 유물 | 달빛 인장 (2026-10-29 추가) |
|---|---|---|---|---|
| 모든 데일리 판 (승패 무관, `EndBattle` 경유) | 평소 공식(`SoulRewardCalculator`) + 개인 보상 유물(`SoulBonus`/`XpBonus`/`LoseSoulBonus`) | - | 평소 드랍 굴림 **없음** | `floor(sealPerFinish(3) x 연속 배율 + 0.5)` |
| 그날 **첫 승리** | 위와 같음 | `floor(firstWinSouls x 연속 배율)` 소울 가산 | **1개 확정 굴림** | 위 판 종료분 + `floor(sealFirstWin(5) x 연속 배율 + 0.5)` |
| 같은 날 두 번째 이후 승리 | 위와 같음 | 없음 | 없음 | 판 종료분만 |
| 뒤로가기 종료 | 없음 | 없음 | 없음 | 0 |

- **달빛 인장** (몬스터 육성 재화 분리 - 단일 진실 `monster-growth-currencies.md` §2.2): 데일리 판이 끝날 때마다 받는 둥지 숙련 재화. 연속 배율은 위 소울 보너스와 같은 식이지만 **반올림(0.5 올림)** 이고, 판 종료분과 첫 승리분을 각각 반올림한다. 하루 최대(3판 + 첫 승리) 1일 14 → 7일 이상 23. 결과창 `보상` 줄에 `+N 달빛 인장` 칩으로 표시(§9.4). 해금은 데일리와 같은 `unlockClearedStage`. 수치 필드 `sealPerFinish`·`sealFirstWin` 은 `DailyConfig.json` 에 있다(§4.2 표에 추가된 필드).

- **연속 배율** = `1 + streakBonusPerDay x (Min(DailyStreak, streakBonusMaxDays) - 1)` (이번 판으로 갱신된 연속 값 기준). 팝업 미리보기(문구 1450 인자)도 같은 값을 쓴다 - 오늘 아직 끝낸 판이 없으면 `예상 연속 = (어제 행 존재) ? DailyStreak + 1 : 1`, 이미 끝낸 판이 있으면 `DailyStreak`. 1일 x1.0 = 150 / 3일 x1.2 = 180 / 7일 이상 x1.6 = 240. 검산: 1 + 0.10 x (3 - 1) = 1.2, 150 x 1.2 = 180 / 1 + 0.10 x 6 = 1.6, 150 x 1.6 = 240.
- **확정 유물 굴림**: `relics.md` §2.4 의 2단계 굴림(등급 → 유물)을 그대로 쓰되 확률 단계를 건너뛴다(chance 1.0). 영웅 테이블 = 그날 영웅, 등급 가중 = `DailyConfig.difficulty`(Normal) 행, 최대 중첩 유물 제외 규칙 동일. 후보가 0 이면 미획득(결과창 줄 없음). (2026-11-01 현행: 유물 잔해 규칙이 켜진 뒤로는 뽑힌 등급의 유물이 모두 최대 중첩이면 유물 대신 그 등급의 잔해를 주므로, 확정 굴림은 항상 유물이나 잔해 중 하나를 준다 - `monster-growth-currencies.md` §2.4. "미획득" 은 영웅 테이블 자체가 비었거나 육성 데이터 로드 실패 때만.) **`RelicMissStreak` 은 읽지도 쓰지도 않는다**(데일리 확정 보상이 챕터 판의 천장 진행을 건드리지 않게).
- 경제 검산: 데일리 판 자체는 평소 판과 같은 보상식이라 판수만큼 평소 경제를 따른다. 데일리가 **추가로** 주는 소울은 하루 최대 240(7일 연속 첫 승리) = 평균 승리 1판(212, `village-meta-hub.md` §2.3) 의 1.13배(240 ÷ 212 = 1.132). 매일 받으면 상점 전 항목 만렙(49런 분량) 도달이 하루 1.13판씩 당겨지는 셈이며 이 가속 폭은 게이트 DQ5 로 판정한다. 확정 유물 하루 1개는 52 슬롯 대비 수집 속도를 올리는 의도된 재방문 보상이다(게이트 DQ5).

### 7.2 연속 일수 - 대안 비교

| 안 | 내용 | trade-off | 판정 |
|---|---|---|---|
| A. 없음 | | 재방문 장치가 "오늘의 조합" 뿐. 가설 (1) 의 측정 축이 약하다 | 기각 |
| **B. 참가 기준 연속, 첫 승리 보너스에만 배율 (권장)** | 그날 데일리 1판을 **끝내면**(승패 무관) 참가 1일. 끊기면 1부터 | 진 날도 연속이 유지돼 약한 플레이어가 이탈하지 않는다. 배율은 승리 보너스에만 걸려 경제 영향이 상한 240 으로 묶인다 | **채택** |

## 10. 코드 접점 · 연동 가정

### 10.1 데일리 전투 컨텍스트 (핵심 접점)

현행 `BattleController` 는 스테이지 행·규칙(`GetRules`)·영웅·배경·외형·유물 드랍·랭킹 제출·진행 갱신을 모두 `profile.SelectedStage` 에서 읽는다. 데일리는 다음 명세로 이를 우회한다(구조는 gameplay-programmer 판단).

- **세션 전용 컨텍스트**(저장 안 함): `dayIndex`, `heroId`, 기준 스테이지(챕터·인덱스), 상시·페이즈 규칙 프리셋 키, 오늘의 유물 2개(+중첩), 난이도, 카드 시드 2개, `comboKey`. 데일리 팝업의 시작 버튼이 만들고 Battle 이 읽는다.
- **`SelectedStage` 를 절대 쓰지 않는다**(데일리 후 마을로 돌아오면 챕터 선택이 그대로).
- 컨텍스트가 있을 때 Battle 의 입력 대체:

| 입력 | 평소 | 데일리 |
|---|---|---|
| 영웅 직업·HP·공격력 | `SelectedStage` 의 챕터 영웅 · 스테이지 배율 · `EffectiveDifficulty` | 컨텍스트 영웅 · 기준 스테이지 배율 · `DailyConfig.difficulty` (`HeroStatCalculator` 같은 1회 반올림) |
| 배경 · 영웅 외형 | `SelectedStage` | 기준 스테이지 |
| 스테이지 규칙 | `GetRules(SelectedStage)` | 프리셋 2개 (`StageRuleRunner` 에 같은 형태로 전달) |

- **도전 차감 저장 시점**: 영웅 스폰 직후 `DailyDays` +1 후 즉시 로컬 저장(앱 강제 종료로 차감을 피하지 못하게).
