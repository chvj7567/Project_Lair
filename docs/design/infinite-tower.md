## § 헤더

- **목표**: 챕터 스테이지(1-1~5-5)와 별개인 엔드게임 모드 **무한의 탑**을 만든다. 층이 오를수록 영웅(5직업)과 규칙 묶음(기존 스테이지 규칙 재사용) 조합이 바뀌고 영웅 능력치가 기하급수로 커지며, 플레이어는 끝없이 위층에 도전한다. 최고 층은 시즌별 리더보드로 겨룬다.
- **검증 가설**: (1) 챕터를 다 깬 플레이어가 "같은 판을 반복한다"고 느끼던 지점에서, **매 층 새 조합 + 한 층 더** 루프가 재방문 동기를 만드는가. (2) 결정적(시드 고정) 층 구성 + 최고 층 리더보드가 v0.3 검증 가설의 "경쟁 동기"를 챕터 최단 기록보다 강하게 만드는가. (3) 기존 자산(영웅 5직업·규칙 6종·유물·상점)만으로 층별 체감 난이도가 고르게 오르는가(신규 몬스터·규칙 0).
- **현재 단계 범위 적합성**: **범위 밖 항목의 명시 승격 요청 - 사용자 승인 필요.** CLAUDE.md §8 은 "무한 탑"을 세 문장에서 금지한다(§12 에 원문 인용). 승격 문구 초안은 §12 에 있으며 **승인 전에는 구현에 착수하지 않는다.** 서버 쪽은 Firebase 클라이언트 연동 코드만 추가한다(신규 컬렉션 제출/조회). Firestore 보안 규칙 변경은 이 레포 범위 밖이며 §7.4 에 콘솔 작업 의존성으로 적는다. 별도 메인 메뉴 금지 유지(진입은 마을 HUD 버튼 → 팝업). ★ 목표 · 신규 몬스터 · 신규 스테이지 규칙 · 탑 전용 상점/재화는 이번 범위 밖.
- **핵심 메커니즘**: (a) 층 N 의 구성(영웅 · 규칙 묶음 · 능력치)은 `(시즌 시드, N)` 만으로 정해지는 **순수 결정 함수**다. 모든 플레이어가 같은 N층을 만난다. (b) 5층이 한 **구간**이고 구간 안에서 영웅 5명이 한 번씩, 5번째 층은 보스층이다. 규칙은 기존 25개 스테이지의 규칙 묶음을 템플릿으로 재사용한다. (c) 층을 깨면 저장되고 다음 층이 열린다. 지면 같은 층에 다시 도전한다(클리어한 층 재도전 없음). 결과창의 "다음 층" 버튼으로 마을을 거치지 않고 계속 오를 수 있다.

## 1. 핵심 루프와 동기

### 1.1 루프

```
마을 → [탑] 버튼 → 탑 팝업 (다음 층 미리보기 · 랭킹) → 도전 · N층
   → 전투 (5분 · 카드 픽 · 기존 규칙 그대로)
   → 승리: N층 저장 · 소울/XP · 유물 굴림 · 랭킹 제출 → 결과창 [다음 층] → N+1층 전투 …
   → 패배: 소울/XP(패배 공식) · 유물 굴림(1/4) → 결과창 [다시 도전] → N층 재도전
   → [마을로] → 상점/유물 도감 정비 → 다시 탑
```

### 1.2 동기 구조

| 동기 | 장치 | 근거 |
|---|---|---|
| 새 판 | 층마다 영웅 x 규칙 묶음이 바뀐다. 25개 템플릿 x 영웅 5 = 125 조합(보스/일반 분리) | "같은 판 반복" 해소의 직접 수단 |
| 한 층 더 | 결과창 "다음 층" 으로 마을 왕복 없이 연속 등반 | 5분 런 x 연속 = 세션 길이를 플레이어가 정함 |
| 계획 | 다음 4층까지 구성이 미리 보인다(§6.2) | 결정적 생성이라 가능. 카드 축 선택·출격 타이밍을 계획 |
| 경쟁 | 시즌별 최고 층 리더보드(동층은 그 층 클리어 시간) | v0.3 가설 "경쟁 동기" |
| 메타 회수 | 탑 승리마다 유물 굴림(높은 층일수록 희귀 등급 가중) | 유물 2차 수집 루프를 엔드게임에 연결 |

### 1.3 페이싱

- 한 층 = 한 전투(최대 300초). 결정 빈도·카드 임계는 챕터와 동일(컨셉서 §4.2 불변).
- 층 1 기준 처치 시간: 5-5 를 막 깬 플레이어(M 1.3, §3.4) 200초, 메타 완성(M 2.0) 130초. 컨셉서 §8 목표 밴드(120~240초) 안에서 시작한다.
- 구간(5층) 1회 등반은 승리 기준 5전투. 1층 처치 시간 200초(M 1.3)와 130초(M 2.0)의 평균 165초에 카드/결과 체류 30초를 더하면 5 x 195 = 975초(16분 15초).

## 2. 대안 비교 (핵심 결정)

### 2.1 판 사이 진행 - 연속 도전 vs 층 단위 저장

| 안 | 내용 | trade-off | 판정 |
|---|---|---|---|
| A. 연속 런(1층부터, 1패 = 종료) | 클래식 로그라이크 탑 | 20층 = 20 x 5분 = 최대 100분 한 판. 매번 1층부터라 **같은 저층을 반복**(해결하려는 문제 재발). 모바일 세션 부적합 | 기각 |
| **B. 층 단위 저장(권장)** | 깬 층은 영구 저장, 다음 층이 열림. 지면 같은 층 재도전. 결과창 "다음 층" 으로 연속 등반 | 매 승리가 새 콘텐츠. 세션을 끊어도 손실 없음. 단점: 벽 층에서 같은 층 반복(§2.4) | **채택** |
| C. 구간 체크포인트(5층마다 저장, 구간 안 1패 = 구간 처음) | 긴장감 추가 | 보스층에서 지면 일반 4층을 다시 해야 해 반복이 다시 생긴다. 상태(구간 내 진행) 저장 규칙 추가 | 기각 |

- **클리어한 층은 다시 도전할 수 없다.** 탑 전투는 항상 "최고 층 + 1"(이하 **도전 층**)이다. 이유: 유물 파밍 경로를 챕터와 같게 유지(탑 승리 = 새 층 = 굴림 1회), 기록 의미 단순화.

### 2.2 층 생성 - 결정성

| 안 | 내용 | trade-off | 판정 |
|---|---|---|---|
| A. 도전마다 무작위 | 재도전 시 구성이 바뀜 | 벽 층이 "운 좋은 조합 나올 때까지 재도전" 으로 변질, 랭킹 비교 불가 | 기각 |
| **B. 시즌 시드 고정(권장)** | 층 N 구성 = f(시드, N). 모든 플레이어 동일 | 공정한 랭킹, 미리보기·공략 공유 가능, 저장은 층 번호 하나로 충분(생성 상태 저장 0) | **채택** |
| C. 날짜 시드(매일 변경) | 일일 변주 | 층 진행 저장과 충돌(어제 깬 10층이 오늘 다른 층). 일일 콘텐츠는 `daily-challenge.md` 소관 | 기각 |

- 전투 자체의 난수(카드 제시 등)는 기존대로 매 판 다르다. 결정적인 것은 **층 구성**뿐이다.
- 시즌 교체는 데이터(`TowerConfig.seasonId`·`seed`) 수정으로만 일어난다. 자동 교체 없음(§4.6, D-12).

### 2.3 영웅 HP 정규화 - 직업 HP 정체성 유지 여부

| 안 | 내용 | trade-off | 판정 |
|---|---|---|---|
| **A. HP 정규화(권장)** | 같은 층이면 어느 직업이든 영웅 HP 가 같다(`hpScale x 탑 HP 보정 = 1.00`) | 층 간 체감 난이도가 직업 뽑기에 덜 흔들린다(랭킹 공정성). 챕터 데이터도 이미 사실상 정규화돼 있다: 처치 시간 등가 배수 `eq = hpScale x hpMultiplier` 가 전 챕터 공통 도출식(`chapter-system.md` §4.3, 예 2-1: 0.8 x 1.56 = 1.248 ≈ eq 1.25, 4-1: 1.25 x 1.28 = 1.60 = eq 1.60). 직업 정체성은 AI·스킬·공격력으로 남는다 | **채택** |
| B. `hpScale` 그대로 | 층 HP = 앵커 x hpScale x 층 배율 | 광전사 층 HP 가 암살자 층의 1.25 ÷ 0.7 = 1.79배 → 같은 층대에서 처치 시간 79% 편차. 보스층이 광전사면 사실상 벽 | 기각 |

- 공격력은 정규화하지 않는다: 각 직업의 챕터 보스 스테이지 `powerMultiplier`(1.50/1.60/1.75/1.85/1.95)를 그 직업의 탑 기준값으로 재사용해 챕터 설계자가 AI 별로 맞춘 공격 압박을 유지한다(§3.2).

### 2.4 벽 층 반복 - 핵심 동기 위험

층 단위 저장 + 결정적 생성의 귀결로, 실력/메타 한계에 닿은 플레이어는 **같은 층을 반복**한다. 이 기획이 풀려는 문제와 같은 증상이라 별도로 결정한다.

| 안 | 내용 | trade-off | 판정 |
|---|---|---|---|
| **A. 고정 + 메타 회수(권장, 1차)** | 벽 층은 그대로. 패배에도 소울(패배 공식)·유물 굴림(1/4)·영주 XP 가 쌓이고, 다음 4층 미리보기로 "이 층만 넘으면" 목표가 보인다 | 구현 0 추가. 벽은 무한 모드의 정상 상태이고 상점/유물이 오르는 수단. 단 상점 만렙 이후 소울 가치가 떨어진다(R3) | **채택** |
| B. 실패 누적 완화 | 같은 층 3패마다 그 층 영웅 HP -3% | 체감 구제는 크나, 같은 층이 사람마다 다른 난이도가 되어 랭킹 비교 의미가 깨진다(시도 횟수 저장·랭킹 표기 추가 필요) | 기각 |
| C. 층 재구성권 | 같은 층 3패 후 그 층 구성(영웅·규칙)을 한 번 다시 굴림(재구성 횟수를 세이브, 생성 입력에 포함) | 상성 나쁜 조합 회피 가능. 결정성은 유지되나 플레이어마다 층 구성이 갈려 공략 공유·랭킹 공정성이 약해짐 | 후속 후보(R2 지표 미달 시) |

- **결정 메트릭**: qa-simulator 게이트 T3(§9) "벽 직전 층 도전 횟수 중앙값" 이 3회를 넘으면 C 안을 별도 승인 요청한다.

## 3. 층 규칙과 수치

### 3.1 층 구조

- **구간(band)** `b = ceil(N / 5)`, **구간 내 위치** `p = ((N - 1) mod 5) + 1`. `p = 5` 는 보스층.
- 구간 크기 5 는 `StageProgress.StagesPerChapter`(5) 와 같은 값을 쓴다. 위치 p 는 영웅 외형 단계(`HeroStageVariantConfig` 의 1~5단계)로도 쓰여 보스층은 그 직업의 보스 외형(확대 1.20~1.35)으로 나온다.
- 영웅: 구간마다 탑 등장 영웅 5명을 시드로 섞어 p = 1~5 에 한 명씩 배정. **구간 안 중복 없음**, 구간 경계에서도 직전 층과 같은 영웅 금지(§3.5).
- 규칙 묶음: 기존 스테이지 25개의 규칙 세트(`Stage_Rule` 의 (chapterId, stageIndex) 묶음)를 템플릿으로 쓴다.
  - 일반층(p = 1~4): `stageIndex` 1~4 템플릿 20개 중 해금된 것(`minFloor <= 구간 첫 층`)에서 구간당 **서로 다른 4개**.
  - 보스층(p = 5): `stageIndex` 5 템플릿 5개 중 해금된 것에서 1개. **직전 구간 보스 템플릿과 다른 것**(후보가 2개 이상일 때).
  - 보스 템플릿은 원래 트리거 HP 비율(0.75/0.55/0.35)을 그대로 쓰므로 같은 묶음 안 트리거 충돌이 없다(기존 데이터 검증 통과분).
- 배경: **영웅 직업의 챕터 배경**(`Chapter.backdropKey`). 규칙 템플릿 출처 챕터와 무관.
- 영웅 스킬·AI·외형: 그 직업의 기존 것 그대로(`hero_skills.json` loadout · `aiType` · `HeroStageVariantConfig` 의 (영웅 챕터, p) 엔트리).

### 3.2 능력치 공식

```
floorHp(N)    = hpBase x (1 + hpGrowthPerFloor)^(N-1) x (p == 5 ? bossHpMul : 1)
floorPower(N) = (1 + powerGrowthPerFloor)^(N-1) x (p == 5 ? bossPowerMul : 1)
  (두 값 모두 상한 multiplierCap 으로 절단)

영웅 HP    = round_half_up( 앵커HP    x hpScale    x HeroArchetype_Tower.hpMultiplier    x floorHp(N) ÷ Stage_Tower.ruleFactor )
영웅 Power = round_half_up( 앵커Power x powerScale x HeroArchetype_Tower.powerMultiplier x floorPower(N) )
range / cooldown / moveSpeed = 직업 값 그대로
```

- 곱 전체를 **decimal 로 1회만 반올림**(`StageProgress.ScaleHeroStat` 4인자 오버로드 `(앵커, 직업 배율, 배수A, 배수B)` 의 계산 규약과 동일: 배수A = 탑 영웅 보정, 배수B = 층 배율 ÷ ruleFactor). 최소 1.
- **ruleFactor 보정**: 챕터 `Stage.json` 의 `hpMultiplier` 는 규칙이 영웅을 돕는 만큼(회복 샘·봉인·결계 등) 이미 나눠 둔 값이다(`chapter-system.md` §4.1). 탑도 템플릿마다 같은 계수로 나눠, 규칙 많은 층이 규칙 없는 층보다 최대 12% 어려워지는 스파이크를 없앤다. 초기값은 각 챕터 기획서의 ruleFactor 그대로(§4.4). 단 챕터 계수는 **그 챕터 영웅 기준**(체류율·봉인 종 비중)이라 다른 직업과 섞인 조합은 미검증 → 게이트 T2.
- 난이도 배율(`Difficulty.json`)은 탑에 적용하지 않는다(탑 곡선이 난이도를 대신함, D-9).

복리 계수: 1.035^4 = 1.147523 · ^9 = 1.362897 · ^14 = 1.618695 · ^19 = 1.922502 · ^24 = 2.283329 · ^29 = 2.711878 / 1.015^4 = 1.061364 · ^9 = 1.143390 · ^19 = 1.326951 · ^24 = 1.429504 · ^29 = 1.539983.

| 10 | 보스 | 2 x 1.362897 x 1.10 = 2.998 | 11993 | 1.143390 x 1.05 = 1.201 |

(1.015^14 = 1.143390 x 1.077284 = 1.231756. 정규화 HP = 4000 x floorHp, 예 25층 4000 x 5.023324 = 20093.)

**시간 예산 모델**(초기 모델, 검증 전): 챕터 도출식 `처치 시간 ≈ T1 x eq ÷ M`(T1 = 130, `chapter-system.md` §4.3)을 탑에 적용하면 `처치 시간 ≈ 130 x floorHp ÷ M`. M 은 플레이어 메타(상점·유물) + 빌드의 압력 계수.

| 플레이어 상태 | M 가정 | 1층 처치 시간 | 300초 넘는 첫 층(벽) | 산식 |
|---|---|---|---|---|
| 5-5 막 클리어 | 1.30 | 130 x 2.0 ÷ 1.3 = 200초 | **13층** | 임계 floorHp = 300 x 1.3 ÷ 130 = 3.000. 12층 2 x 1.035^11 = 2.920 통과, 13층 2 x 1.035^12 = 3.022 초과 |
| 상점 중반 + 유물 일부 | 1.60 | 162.5초 | **19층** | 임계 3.692. 18층 2 x 1.035^17 = 3.589 통과, 19층 2 x 1.035^18 = 3.715 초과 |
| 상점 만렙 + 유물 풀셋 | 2.00 | 130초 | **25층(보스)** | 임계 4.615. 24층 2 x 1.035^23 = 4.412 통과, 25층 5.023 초과 |

- M 2.00 근거: 상점 만렙 +30.8%(`village-meta-hub.md` §3.3) x 유물 풀셋 1.48~1.68(`relics.md` §1.3) = 1.308 x 1.48 = 1.94 ~ 1.308 x 1.68 = 2.20 의 하단.
- 의도: 메타 성장이 벽을 12층 안팎 → 25층 안팎으로 끌어올려 "유물·상점을 모으면 더 높이 간다" 가 보이게 한다. 빌드 편차(카드 운)로 벽은 ±2~3층 흔들린다고 보고, 이 폭은 T1 게이트로 확인한다.
- **결정 메트릭**: 위 모델은 HP 비례 가정(공격력 상승·규칙·빌드 편차 무시)이라 최종값은 qa-simulator 검증 후 결정한다(§9 T1·T4·T5). 조정 레버는 `TowerConfig` 숫자뿐(코드 변경 0).

### 3.5 생성 알고리즘 (결정성 계약)

플랫폼·기기 간 같은 결과를 보장해야 랭킹이 공정하므로 난수 함수까지 고정한다. `UnityEngine.Random` · `System.Random` 사용 금지(구현 버전별 시퀀스 차이 위험).

```
난수: SplitMix64
  next(): state += 0x9E3779B97F4A7C15
          z = state
          z = (z ^ (z >> 30)) * 0xBF58476D1CE4E5B9
          z = (z ^ (z >> 27)) * 0x94D049BB133111EB
          return z ^ (z >> 31)                       (ulong, 오버플로 wrap)
  스트림 초기 state = (ulong)(uint)seed ^ ((ulong)band << 32) ^ salt   (seed 는 0 이상, §4.5)      salt: 영웅 1 / 일반 템플릿 2 / 보스 템플릿 3
  섞기: Fisher-Yates, i = n-1 → 1, j = next() % (i+1)
  입력 정렬: 섞기 전 영웅은 heroId ordinal 오름차순, 템플릿은 (chapterId, stageIndex) 오름차순 (JSON 행 순서 무관)

구간 b = 1, 2, 3, … 순서로 계산(구간 b 는 b-1 의 결과를 참조, 결과는 메모이즈):
  영웅:   H = shuffle(탑 영웅 전체, stream(b, 1)) 앞 5명.  b > 1 이고 H[0] == 직전 구간 H[4] 이면 H[0] ↔ H[1] 교환
  일반:   R = shuffle({ stageIndex 1~4 이고 minFloor <= 5b-4 }, stream(b, 2)) 앞 4개 → p = 1..4 에 순서대로
  보스:   B = shuffle({ stageIndex 5 이고 minFloor <= 5b }, stream(b, 3)).  B[0] 이 직전 구간 보스와 같고 후보가 2개 이상이면 B[1]
  층 5(b-1)+p 의 구성 = (H[p-1], p<5 ? R[p-1] : 보스)
```

- 탑 영웅이 5명보다 많아지면(후속 챕터) 구간마다 앞 5명만 쓴다. 5명보다 적으면 로드 오류(§4.5).
- 층 1000 까지 계산해도 구간 200개 x 섞기 3회라 비용이 무시할 수준이다. 팝업·전투 진입 시 필요한 층까지 계산하고 메모이즈한다.
- **같은 시드에서 템플릿·영웅 데이터가 바뀌면 층 구성이 바뀐다.** 그래서 탑 관련 데이터(`Stage_Tower`·`HeroArchetype_Tower`·`Stage_Rule*` 중 템플릿으로 쓰이는 행)를 바꿀 때는 시즌을 올린다(§4.6, R6).

### 4.3 조회 헬퍼 (의도만, 시그니처는 gameplay-programmer 판단)

- `GetTowerHighestFloor()` / `GetTowerFloorClearTime(floor)`: 조회 부수효과 0.

### 4.5 로드 검증 (위반 시 로드 오류, `ChapterDatabase` 오류 수집 패턴 재사용)

1. `TowerConfig`: `seasonId >= 1`, `seed >= 0`, `1 <= unlockClearedStage`, `hpBase > 0`, 두 growth `>= 0`, 두 boss mul `>= 1`, `multiplierCap >= 1`, `1 <= relicNormalFromFloor <= relicHardFromFloor`, `previewFloors >= 0`, `leaderboardTop` 1~50.
2. `HeroArchetype_Tower`: `heroId` 중복 없음, `HeroArchetype` 에 존재, 그 영웅을 쓰는 챕터가 `Chapter.json` 에 정확히 1개 존재(배경·외형·유물 키의 출처), 두 배율 `> 0`, **행 수 >= 5**(구간 5층 배정).
3. `Stage_Tower`: (chapterId, stageIndex) 중복 없음, `Stage.json` 에 존재, `minFloor >= 1`, `ruleFactor >= 1.0`. **minFloor 1 인 일반 템플릿(stageIndex 1~4) >= 4개, minFloor <= 5 인 보스 템플릿 >= 1개.**
4. 로드 실패 시: 오류 로그 후 "탑 비활성" - 마을 탑 버튼은 보이되 누르면 토스트 "준비 중"(기존 문구 1322), 저장된 탑 진행은 삭제하지 않는다. 챕터·유물·클라우드는 정상.

### 4.6 시즌 규칙

- 시즌 교체 = 개발자가 `TowerConfig.seasonId` 를 올리는 데이터 변경(필요하면 `seed` 도). 자동 주기 교체 없음.
- 교체 후 첫 읽기(마을 탑 팝업 열기 · 탑 전투 시작)에서 `NormalizeTowerSeason` 이 이전 시즌 진행을 지운다. **이전 시즌 최고 층은 보관하지 않는다**(D-12). 이전 시즌 랭킹 문서는 서버에 남지만 클라이언트는 현재 시즌만 조회한다.
- `TowerConfig` 로드 실패 상태에서는 지우지 않는다(데이터 복구 시 보존).

### 7.2 리더보드 (클라이언트 측)

- **신규 컬렉션 경로**: `towerLeaderboard/{seasonId}/entries/{uid}` (시즌별 하위 컬렉션). 기존 `stageLeaderboard` 는 재사용하지 않는다 - 그쪽 `ShouldReplace` 는 "낮을수록 좋음"(클리어 시간) 규약이다.
- 문서 필드: `uid`(string) · `season`(int) · `displayName`(string, `MetaProfile.ResolveDisplayName` 규약) · `floor`(int, 최고 층) · `clearTimeMs`(int, 그 층 클리어 시간 ms) · `hero`(string, 그 층 영웅 heroId) · `score`(**long**).
- `score = floor x 1,000,000 + (300,000 - clearTimeMs)`. `clearTimeMs` 는 1~300,000(5분 상한)이라 두 번째 항이 0~299,999 로 층 자리를 침범하지 않는다. 예: 17층 2:30.0 → 17,000,000 + 150,000 = 17,150,000. 높을수록 상위, 같은 층이면 빠른 클리어가 상위.
- 제출: 탑 승리 직후 1회 + 팝업 열 때 로컬 최고 기록 1회 재제출(오프라인 실패분 복구). 트랜잭션으로 기존 `score` 보다 클 때만 쓴다(`SubmitStageScoreAsync` 의 트랜잭션 패턴, 비교 방향만 반대). 실패는 조용히 로그(기존 best-effort 규약, 게임 흐름 차단 없음).
- 조회: 상위 = `entries` 를 `score` 내림차순 `leaderboardTop`(10)개. 내 순위 = `score` 가 내 값보다 큰 문서 수 + 1(기존 `GetMyStageRankAsync` 방식).
- 순수 헬퍼 `TowerLeaderboard`(`StageLeaderboard` 와 같은 위치·형태): 경로 생성, `score` 인코딩/디코딩, `ShouldReplace(existingScore, newScore) = newScore > existingScore`, 입력 범위 검증(`floor >= 1`, `1 <= clearTimeMs <= 300,000`).

### 7.3 공정성 메모

- 2배속 유물(`HasteHourglass`)은 게임 시간 기준이라 `clearTimeMs` 척도가 같다(`relics.md` §5.3, D-6 결정 유지).
- 유물·상점 보유량 차이는 랭킹에 그대로 반영된다(메타 경쟁이 의도).

### 7.4 의존성 - Firebase 콘솔 작업 (이 레포 범위 밖, 사용자 작업)

탑 랭킹 제출 전에 사용자가 Firestore 보안 규칙에 다음 동작을 추가해야 한다. 규칙 변경 전에는 제출이 서버에서 거부되며 클라이언트는 조용히 실패한다(팝업 랭킹 패널은 "랭킹을 불러오지 못했습니다" 표시).
1. 경로 `towerLeaderboard/{seasonId}/entries/{uid}` 읽기: 로그인 사용자 전체 허용.
2. 쓰기(생성·수정): 요청자 uid == 경로 `{uid}` == 문서 `uid` 필드.
3. 필드 타입·범위: `season` 정수 == 경로 `{seasonId}`, `floor` 정수 1~10,000, `clearTimeMs` 정수 1~300,000, `score` 정수 == `floor x 1,000,000 + 300,000 - clearTimeMs`, `displayName` 은 기존 리더보드 규칙과 같은 제한, `hero` 문자열.
4. 수정은 새 `score` 가 기존 `score` 보다 클 때만(단조 증가).
5. 인덱스: 하위 컬렉션 단일 필드 `score` 정렬이라 자동 단일 필드 인덱스로 충분(복합 인덱스 불필요).
- 한계: 클라이언트가 층을 건너뛴 값을 제출하는 것은 규칙으로 막을 수 없다(서버 검증은 Cloud Functions 범위, 이 레포 밖). 위험 R7.

## 11. 연동 가정 (동시 작성 문서 · 공용 자원)

### 11.1 MetaProfile 버전 번호

- 본 문서는 **v8 → v9** 로 쓴다. `dungeon-formation.md` · `daily-challenge.md` 도 세이브 필드를 추가하면 같은 번호를 노릴 수 있다. 규칙: **먼저 구현되는 기획이 9, 그다음이 10 …**. 탑 마이그레이션 단계(§5.1)는 버전 비교 없이 매번 수행되는 멱등 정리라 번호가 바뀌어도 내용은 같다.

### 11.2 던전 편성 (`dungeon-formation.md`)

`dungeon-formation.md`(같은 날 작성 중, 읽기만 함) 기준으로 맞춘 가정:
- **출격 흐름**: 편성 기획 §10.1 은 "탑 층 출격 전에도 `EUI.FormationPopup` 을 재사용하고 요약 패널(층 정보·규칙)만 탑이 채운다" 고 가정한다. 이 문서도 그 가정을 받는다 - 편성이 승격되면 탑 팝업 "도전" → `FormationPopup`(요약 = 도전 층의 영웅·규칙) → 출격. 편성 미승격 상태에서는 §6.3 대로 탑 팝업에서 바로 출격.
- **편성 저장**: 탑 전용 편성을 두지 않는다. 공용 `MetaProfile.Formation` 1개를 쓴다(편성 기획의 가정과 일치). 층마다 다른 편성 상한(편성 기획 §10.1 훅)은 쓰지 않는다.
- **봉인된 둥지**: 편성 기획 §5.1 C 안("정확히 1곳 봉인 + 봉인 종이 없으면 코스트 최고 둥지 1곳 봉인")이 채택되면 탑의 SealedNest 템플릿도 같은 규칙으로 동작한다. 이 경우 `Stage_Tower.ruleFactor` 의 SealedNest 계수(챕터 기본 편성 가정)가 달라질 수 있어 탑 게이트 T2 와 편성 게이트 F3 결과를 함께 본다.
- 편성은 탑 층 구성(시드 결과)에 영향을 주지 않는다 - 결정성 유지.

### 11.3 일일 도전 (`daily-challenge.md`)

`daily-challenge.md`(같은 날 작성 중, 읽기만 함) 기준으로 맞춘 가정:
- **전투 모드**: 데일리도 `SelectedStage` 를 건드리지 않는 "세션 전용 데일리 전투 컨텍스트" 로 돈다. 이 문서의 §8.1 "전투 사양 단일 해석 지점" 과 같은 요구이므로 **한 번만 만들어 두 모드가 공유**한다(먼저 구현되는 쪽이 만들고 다른 쪽은 모드 하나를 추가). 모드 구분은 `EBattleMode { Chapter, Tower }` 에 데일리가 `Daily` 를 append 한다. 두 기획이 별도 모드 Enum 을 만들지 않는다.
- **난수**: 데일리도 SplitMix64 를 쓴다(그 문서 §2). 상수·믹스 함수가 §3.5 와 같으므로 같은 순수 유틸을 공유하고, 스트림 초기값만 다르다(탑 = `TowerConfig.seed` 기반, 데일리 = 코드 상수 `DailySalt` 기반 - 그 문서 L-2 의 "탑은 다른 salt" 와 일치). 영웅 배정도 같은 "5개 블록 순열 + 경계 교환" 방식이라 순열 함수를 공유할 수 있다.
- **마을 HUD 배치**: 데일리가 좌 메뉴 (144,488) 를 쓴다(그 문서 L-3). 탑은 하단 바 (818,632) 를 써서 **겹치지 않는다**.
- **Strings_Ko**: 데일리는 1393~1420 을 연속 배정하고 "무결성 테스트가 id 연속성을 검사해 빈 블록 예약 불가" 로 적었으나, 실제 테스트는 블록 단위 범위만 검사한다(`RelicDataTests` 441행 1338~1392, `WorldMapStringsAndPrefabTests` 43·53·57행 1301~1326 / 1201~1206 / 1221~1226, `DifficultyDataAndStatTests` 368행 1327~1334). 따라서 탑의 전용 블록 1601~1624 는 데일리·편성의 1389/1393 이후 연속 구간과 겹치지 않는다.
