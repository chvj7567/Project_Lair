# Firebase 백엔드 피벗 (Spec 1 — 익명 인증) — 도메인 기획서

- **작성일**: 2026-07-14
- **단계**: Project Lair v0.3 (서버 연동 클라이언트)
- **상위 문서**: spec `docs/superpowers/specs/2026-07-14-firebase-backend-pivot-design.md` · plan `docs/superpowers/plans/2026-07-14-firebase-backend-pivot.md`
- **계승 기획서**: `docs/design/unity-server-integration.md` — **플레이어 대면 UX·문구·레이아웃의 단일 진실.** 본 피벗은 그 문서를 대체하지 않고 계승한다.
- **역할 분담**: spec=무엇을(백엔드 교체) / plan=어떻게 단계별 / 계승 기획서=UX·문구·레이아웃 / **본 기획서=이 백엔드 교체가 플레이어 경험에 무엇을 바꾸는가(대부분 "안 바꾼다")와 CLAUDE.md §8 문안**.

> **이 기획서의 성격**: 백엔드를 자체 서버(ASP.NET Core+MySQL+Redis)에서 Firebase BaaS 로 교체하는 피벗이다. `ILairApiClient` 인터페이스가 불변이라 모든 UI·서비스·테스트가 그대로 흡수한다. 따라서 본 기획서는 **새 UX 를 설계하지 않는다.** 계승 확인 + 플레이어 대면 델타(거의 없음)·한계 고지 + §8 문안만 담는 얇은 문서다.

## § 헤더

- **목표**: v0.3 서버 연동의 백엔드를 Firebase 로 교체할 때 **플레이어 경험이 무엇이 변하고(거의 없음) 무엇이 새로 한계로 남는지**를 확정하고, CLAUDE.md §8 재작성 확정 문안을 제공한다.
- **검증 가설**: 클라우드 계정·세이브·랭킹이 재방문·기기이전·경쟁 동기를 강화하는가(project.md stage_goal). 본 기획은 그 중 **"백엔드를 바꿔도 검증 대상 UX 가 흔들리지 않는가"** 와 **"익명 인증이 가설의 '기기이전' 축을 어디까지 지탱하는가"** 를 정직하게 정리한다.
- **현재 단계 범위 적합성**: **범위 내.** 서버 연동은 v0.3 승격분(CLAUDE.md §8)이며, 본 피벗은 그 백엔드 구현만 교체한다. 신규 영웅/몬스터/카드 리소스 없음. 구글 로그인(계정 연동)은 **범위 밖(후속 Spec 2)** 이며 본 문서는 그 승격을 **예고만** 한다.
- **핵심 메커니즘**: 인터페이스(`ILairApiClient`) 불변 → 계승 기획서 §1~§6 의 표시명·복원·충돌·랭킹·메뉴·실패톤 UX 는 **코드 변경 없이 그대로 작동**. 플레이어가 체감하는 변화는 없다. 다만 익명 인증이라는 성격상 **기기이전을 여전히 못 푸는 한계**와 **랭킹 안티치트 부재**가 남으며, 이를 §2 에서 정직하게 고지한다.

## §1. UX 계승 확인 — 변화 없음 매트릭스

계승 기획서(`unity-server-integration.md`)의 6개 UX 축은 **본 피벗으로 하나도 바뀌지 않는다.** `ILairApiClient` 시그니처가 불변이고, 각 UX 가 의존하는 결과 타입(`CloudSaveResult` · `DisplayNameStatus` · `RankingRowDto` 등)도 불변이기 때문이다.

| 계승 기획서 § | UX 축 | 피벗 후 | 불변을 보장하는 근거 |
|---|---|---|---|
| §1 | 표시명(`영주 #xxxx` 자동 + 마을 1탭 변경) | **불변** | 표시명은 로컬 전용 + 랭킹 제출 시 동봉. 백엔드 교체와 무관 |
| §2 | 클라우드 복원 확인 프롬프트·성공/없음/실패/오프라인 토스트 | **불변** | `GetSaveAsync`/`PutSaveAsync` 결과 계약 동일. "세이브 없음" = 문서 없음(404/null) 동일 |
| §3 | 409 충돌 → 배지 + 메뉴 진입 시 복원 권유(세션 1회) | **불변** | 충돌은 클라 어댑터(`FirebaseApiClient`) 계층에서 감지되어 `CloudSaveResult.Conflict` 로 동일하게 반환. 배지·권유 로직 그대로 |
| §4 | 랭킹 화면 레이아웃(Top 100·내 순위 하단 고정·컬럼·시간 포맷·행 강조) | **불변** | `GetTopAsync`/`GetMyRankAsync` 가 `List<RankingRowDto>` 로 동일 반환. 내 행 식별 키만 내부적으로 `uid`(string)로 이동(§2.3) — 화면 표기·배치 불변 |
| §5 | 마을 "랭킹"·"클라우드" 2개 메뉴 진입 + CloudPopup 구성 | **불변** | 진입 동선·팝업 구성은 UI 계층. 백엔드 무관 |
| §6 | 오프라인/실패 피드백 톤(직접 행동=토스트, 자동=무음 로그) | **불변** | 실패 판정은 결과 타입 기반. 백엔드 교체로 성공/실패 의미 동일 |

**결론**: 플레이어가 **새로 보거나 배워야 할 화면·문구·동작은 없다.** 신규 UX·신규 문구 설계는 본 피벗 범위 밖이다.

> **내부 인접 변경 2지점(플레이어 비대면, spec §4 명시)** — 순수 "무변경 드롭인"은 아니며 다음 2곳만 인터페이스 인접에서 손댄다. 둘 다 화면에 드러나지 않는다:
> 1. `AuthTokenStore` — `long AccountId` → `string Uid`(Firebase localId). 계정 식별자 타입 변경.
> 2. `RankingRowDto` — "내 행" 식별을 `string uid` 매칭으로. 화면상 `(나)` 강조 표기·기준은 계승 기획서 §4 그대로, 매칭 키만 uid 로. 폴백(내 클리어타임 일치)도 유지.

## §2. 플레이어 대면 영향 / 한계 고지 (정직)

피벗은 UX 를 바꾸지 않지만, **익명 인증 + 서버 부재(BaaS)** 라는 성격상 세 가지 한계를 그대로(혹은 새로) 남긴다. v0.3 는 검증 단계이므로 이를 감수하며, 진짜 해소는 후속 단계로 넘긴다.

### 2.1 익명 인증은 기기이전을 못 푼다 — v0.3 클라우드 세이브의 실가치 재정의

- **한계**: 익명 인증은 재설치·새 기기에서 **새 uid = 새 계정**을 만든다. 옛 세이브(옛 uid 문서)에 접근할 방법이 없다. Firebase 가 이 문제를 새로 만들지는 않지만(자체 서버 익명 인증도 동일했다) **고치지도 않는다.**
- **그래서 v0.3 "클라우드 세이브"가 실제로 지키는 가치는**:
  1. **같은 설치본 내 백업/복원** — 로컬 세이브 유실·기기 초기화 전 클라우드에 있던 데이터 복원. (단 인증이 유지되는 같은 uid 범위)
  2. **랭킹 경쟁** — 최단 클리어를 전역 랭킹에 제출·조회.
- **가설 축과의 관계**: project.md stage_goal 의 세 축(재방문·**기기이전**·경쟁) 중 **"기기이전" 축은 익명 인증만으로는 미검증으로 남는다.** 재방문(백업/복원)·경쟁(랭킹)은 본 Spec 1 로 검증 가능.
- **진짜 기기이전 해소**: 구글 로그인 + 계정 연동(후속 **Spec 2**). 계정을 uid 대신 구글 계정에 묶으면 재설치·기기 교체에서 같은 계정으로 복귀한다. 본 피벗은 그 승격을 **CLAUDE.md §8 에서 예고만** 한다(§3).

### 2.2 랭킹 안티치트 없음 — 서버 권위 부재의 직접 귀결

- **한계**: Firestore-only(서버 코드 없음)에서는 클라이언트가 자기 uid 문서의 `clearTimeMs` 를 **임의 값으로 쓸 수 있다.** 보안 규칙은 "본인 uid 문서에만 쓰기 허용"까지만 강제하고, **값의 정당성은 검증하지 못한다.** 즉 랭킹은 조작 가능하다.
- **플레이어 경험 관점 판단(v0.3)**: **허용한다.** v0.3 은 프리론치 검증 단계로, 검증 대상은 "정밀하게 방어된 경쟁 순위"가 아니라 **"내가 몇 등인지 보이는 것이 재방문·경쟁 동기를 만드는가"** 라는 가설이다. 소규모·비상업 단계에서 조작 인센티브가 낮고, 방어 비용(서버리스여도 Cloud Functions=코드)이 검증 가치를 초과한다. 랭킹 숫자는 **"경쟁 동기 유발 장치"로 읽되 "공식 기록"으로 취급하지 않는다.**
- **미래 경로**: 안티치트는 Cloud Functions(서버리스지만 코드) 또는 별도 검증 계층이 필요하며 **v0.3 범위 밖**이다. 본 한계는 계승 기획서에도 이미 "서버 권위 안티치트는 이후 단계"로 전제돼 있어 **새 후퇴가 아니다.**

### 2.3 표시명 재점유 불가 — 익명 인증 + 잠금 문서의 새 상호작용 (신규 한계 1건)

- **한계**: 표시명 유일성은 `displayNames/{이름}` 잠금 문서로 보장한다(Q3, §4). 그런데 재설치·새 기기의 익명 유저는 **새 uid** 를 받는데, 예전에 쓰던 이름의 잠금 문서는 여전히 **옛 uid** 를 가리킨다. 보안 규칙상 `create` 는 문서가 이미 있어 실패(→ `Taken`), `delete` 는 `request.auth.uid == resource.data.uid` 조건에 걸려 새 uid 가 옛 잠금을 지우지 못한다. **결과 — 재설치한 익명 유저는 자기가 예전에 쓰던 표시명을 다시 못 가져온다**(다른 이름을 골라야 함).
- **이것이 유일한 플레이어 대면 델타다.** §1 매트릭스가 "변화 없음"이라 해도, 익명 인증 + 잠금 문서의 조합은 계승 기획서에 없던 이 한 케이스를 만든다.
- **판단(v0.3)**: **감수한다.** (a) 프리론치·실사용자 0 맥락(§3)에서 실효 피해가 없고, (b) 애초에 재설치 유저는 §2.1 로 진행도 자체를 잃으므로 표시명 재점유는 부차적이며, (c) 근본 해소는 계정이 uid 에 묶이지 않는 **Spec 2(구글 로그인)** 에서 자연히 풀린다. 남는 고아 잠금 문서는 무해하다(누구도 그 이름을 못 쓸 뿐, 다른 이름은 자유). **신규 문구·신규 처리 없음** — 재점유 시도는 기존 `Taken` 토스트(§4)로 그대로 안내된다.

## §3. CLAUDE.md §8 재작성 — 확정 문안

plan Task 7 Step 4 가 **이 문안을 그대로 반영**한다. 아래는 현재 CLAUDE.md §8 의 "서버 연동 허용"·"세이브" 두 bullet 을 대체하고, "계정 연동 승격 예고" 한 bullet 을 추가하는 확정 텍스트다.

### 교체 대상 (현재 §8)

```
- **서버 연동 허용 (2026-06-15 v0.3 승격) — 단 "Unity 클라이언트 ↔ 서버 연동 코드"만 허용** — 익명 기기ID 인증→JWT 로컬 저장, MetaProfile 클라우드 백업/복원, 최단클리어 리더보드 제출/조회 등 클라이언트 측 연동 코드. **서버 구현 자체는 별도 레포(`Project_Lair_Server`, ASP.NET Core+MySQL+Redis) 소관이며 이 Unity 레포에서 서버 코드를 작성하지 않는다.**
- **세이브** — 로컬 JSON 유지 + 클라우드 동기 추가. 전체 MetaProfile 단위로 동기하며, 충돌은 서버가 409 로 처리한다.
```

### 확정 문안 (복사용)

```
- **서버 연동 허용 (2026-06-15 v0.3 승격 · 2026-07-14 Firebase 로 피벗) — 단 "Unity 클라이언트 ↔ 백엔드 연동 코드"만 허용** — 익명 기기 인증→자격증명(idToken·refreshToken·uid) 로컬 저장, MetaProfile 클라우드 백업/복원, 최단클리어 랭킹 제출/조회 등 클라이언트 측 연동 코드. **백엔드는 Firebase BaaS(Firebase Auth + Cloud Firestore, REST over `CHMHttpNetwork`)를 사용하며 운영할 자체 서버가 없다.** 폐기된 자체 서버(`Project_Lair_Server`, ASP.NET Core+MySQL+Redis)는 아카이브하며 그 데이터는 마이그레이션하지 않는다. 서버측 검증·안티치트는 Firestore 보안 규칙이 담당하는 범위까지이며, 그 이상(Cloud Functions 등 서버리스 코드)은 이 레포 범위 밖이다.
- **세이브** — 로컬 JSON 유지 + 클라우드 동기 추가. 전체 MetaProfile 단위로 동기하며, 충돌은 클라이언트가 감지해 기존과 동일한 충돌 UX(배지·복원 권유)로 처리한다.
- **계정 연동(구글 로그인) 승격 예고** — 익명 인증은 기기이전을 풀지 못한다(재설치·새 기기 = 새 계정). 진짜 기기이전을 여는 구글 로그인+계정 연동은 후속 Spec 2 로 v0.3 범위에 편입 **예정**이다(본 Spec 1 에는 포함하지 않는다).
```

> **표현 수준 주의**: §8 은 "무엇이 허용되는가"의 **동작·정책 수준** 문서다. 위 문안은 충돌 처리를 `updateTime` precondition 같은 구현 디테일로 적지 않고 "클라이언트가 감지·기존 UX"로만 적는다. 구현 메커니즘은 spec/plan 이 단일 진실이다.

> **plan delta (반영 완료)**: 이 §8/§2/§9 3곳 동시 리워드는 plan `docs/superpowers/plans/2026-07-14-firebase-backend-pivot.md` Task 7 Step 4 가 반영한다 — 계승 기획서의 'plan delta 보강 대상' 태깅 관례에 맞춘다. (Task 7 이 CLAUDE.md §8 뿐 아니라 §2·§9 레포 지칭까지 함께 리워드하도록 확장 반영 완료.)

### 인접 참조 정합 필요 (§8 밖 — 함께 갱신해야 모순 없음)

## §4. 표시명 유일성 유지 — 플레이어 의미 확인

- **결정(spec Q3)**: 표시명 유일성 검사를 **유지**한다. Firebase 에서는 `displayNames/{정규화이름}` **잠금 문서 + 원자 커밋**으로 구현한다.
- **플레이어 의미**: 이 결정은 **새 UX 를 만들지 않는다.** 인터페이스에 이미 `DisplayNameStatus.Taken` 이 존재하고(자체 서버의 `409 name_taken` 계약), 마을의 표시명 변경 흐름은 이미 `Taken` 을 토스트 **"이미 사용 중인 이름입니다."** 로 안내한다(`VillageController` 현행 동작). Firebase 잠금 문서 패턴은 **동일한 `Taken` 결과를 그대로 재현**하므로, 플레이어가 보는 피드백은 **바이트 단위로 동일**하다. **신규 문구 없음.**
- **요약**: 중복 이름 입력 → 기존과 똑같이 "이미 사용 중인 이름입니다." → 다른 이름 재입력. 백엔드가 바뀌었다는 사실을 플레이어는 알 수 없다.

> **계승 기획서와의 표기 정합 각주**: `unity-server-integration.md` §1 표는 "v0.3 … 중복 검사 없음(서버 미제공)"이라고 적었으나, 이는 **작성 시점의 부정확한 서술**이다 — 실제 인터페이스·구현(`ILairApiClient.DisplayNameStatus.Taken`, `LairApiClient` 의 `409 name_taken` 매핑, `VillageController` 의 Taken 토스트)은 **처음부터 유일성을 강제**해 왔다. 본 피벗은 그 실제 동작을 보존하는 것이며, 계승 기획서의 해당 한 줄은 코드 기준으로 정정해 읽는다(재쟁점화 대상 아님).

## §5. 기존 서버 데이터 폐기 영향 — 플레이어 관점 판단

- **결정(spec Q4)**: 자체 서버 `Project_Lair_Server` 를 폐기(아카이브)하고 Firebase 로 일원화한다. 거기 저장돼 있던(있다면) 세이브/랭킹 데이터는 **마이그레이션하지 않는다.**
- **플레이어 영향 판단**: **무해.** 근거:
  1. **v0.3 는 프리론치 검증 단계**로, 자체 서버에 축적된 **실사용자 데이터가 사실상 없다**(개발/QA 데이터 한정). 버릴 진행도·랭킹이 실질적으로 존재하지 않는다.
  2. 설령 개발 중 축적분이 있어도 **검증용 더미**이며, 랭킹은 §2.2 대로 애초에 "공식 기록"이 아니다. 초기화가 오히려 클린 슬레이트를 준다.
  3. 마이그레이션 도구를 만드는 비용(양 스키마 매핑·이관 검증)은 버릴 데이터의 가치를 크게 초과한다 — YAGNI.
- **플레이어 커뮤니케이션**: 실사용자가 없으므로 **별도 공지·안내 UX 불요.** (실사용자 존재 단계였다면 "데이터 초기화 안내"가 필요했겠으나 v0.3 프리론치엔 해당 없음.)
