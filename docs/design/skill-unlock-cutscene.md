## § 헤더

- **목표**: 영웅 HP 가 스킬 해금 임계(shipped 85/65/45%)에 처음 도달하는 순간, 시간 정지 + 카메라 쉐이크와 함께 "영웅의 '{스킬명}' 스킬 해제" 배너가 좌→중→우로 슬라이드되는 격겜식 컷인을 재생해, 플레이어가 영웅이 방금 얻은 스킬을 확실히 인지하게 한다. (페이즈↔스킬: P1 85% 돌진 강타 → P2 65% 파멸의 노바 → P3 45% 궤도 블레이드 — SoT 는 `hero-skills.md` §1 / shipped `HeroSkillLoadout.asset`.)
- **검증 가설**: 자동전투 중 영웅이 위협적으로 강해지는 순간을 명시적 컷인으로 끊어주면, 플레이어가 "다음 카드픽으로 무엇을 견제해야 하는지" 판단을 더 잘 잡는가. (스킬 해금 = 영웅 강화 = 플레이어가 대응 빌드를 틀 신호)
- **현재 단계 범위 적합성**: **범위 내**. MVP 컨셉서 §11 의 "영웅 1 · 스킬 해금 시스템" 위에 얹는 연출 레이어이며, 게임플레이 수치(데미지·밸런스)를 바꾸지 않는다. 사운드는 호출 seam 만 남기고 미구현 — CLAUDE.md §8 사운드 금지 준수.
- **핵심 메커니즘**: `HeroSkillRunner` 가 해금 순간 이벤트 발행 → `SkillUnlockCutsceneController`(plain C#)가 공유 `PauseService` 로 정지하고, `ICameraShake`(BattleCamera)·`ISkillUnlockBanner`(독립 EUI 팝업)를 unscaled 코루틴으로 A안 순차 구동. 큐 드레인 후 1회 Resume.

## 1. 페이싱 — 타이밍 수치

### 1.1 결정값 (plan 기본값 유지)

| 구간 | 값 | plan sync |
|---|---|---|
| 슬라이드 인 (왼쪽밖→중앙) | **0.35s** | 일치 (`_slideInDuration`) |
| 중앙 홀드 | **1.2s** | 일치 (`_holdDuration`) |
| 슬라이드 아웃 (중앙→오른쪽밖) | **0.35s** | 일치 (`_slideOutDuration`) |
| 쉐이크 (정지 진입 직후) | **0.4s** | 일치 (`ShakeDuration` const) |
| **스킬당 정지 총합** | **1.9s** | 인 0.35 + 홀드 1.2 + 아웃 0.35 |

plan 의 SerializeField/const 기본값을 **조정 없이 확정**한다. 아래 근거 두 축(가독성·끊김)이 모두 통과하기 때문.

### 1.2 근거 — 정지는 5분 예산을 소모하지 않는다

정지 중 게임 타이머도 함께 멈춘다 (정지는 공유 `PauseService` 가 `Time.timeScale` 제어, 배너/쉐이크는 `unscaledDeltaTime` 구동 — spec §7). 따라서 컷인 정지는 **5분 런 예산에서 0초를 소비**한다. 페이싱 판단은 "예산 소모"가 아니라 **(a) 한 런당 끊김 횟수와 (b) 텍스트를 읽을 시간** 두 축으로 한다.

**(a) 끊김 횟수 — 한 런당 3회.** 현재 `HeroSkillLoadout.asset` 의 Phase 는 **3개** (HP 85% / 65% / 45%). 즉 한 런에서 스킬 해금 컷인은 **최대 3회** 발생, 정지 총합 누적 = **1.9s × 3 = 5.7s**. 카드픽 팝업(패시브 HP 10%마다 최대 9회 + 액티브 30초마다)이 이미 정지로 끊는 빈도에 비하면 3회는 희소하다. 5분(300초) 중 컷인이 점유하는 체감 정지는 ~5.7초로, 흐름을 끊는다기보다 **"영웅이 또 강해졌다"는 페이스 변화 마커**로 작동한다. 과하지 않다.

> Loadout Phase 수가 늘면(예 85/65/45 + 1단계 추가 → 4회) 누적도 비례 증가(7.6s). 5회 이상으로 늘릴 경우 홀드를 1.0s 로 줄이는 재검토 트리거를 둔다 — 단 현재 3 Phase 에서는 1.2s 가 적정.

**(b) 읽을 시간 — 홀드 1.2s 검산.** 배너 텍스트는 `영웅의 '궤도 블레이드' 스킬 해제` 형식. 현재 3개 스킬 표시명(`돌진 강타`(P1) / `파멸의 노바`(P2) / `궤도 블레이드`(P3) — Loadout 의 DashStrike·AoeNova·OrbitingBlade `_displayName`)을 대입하면 최장 문자열은 `영웅의 '궤도 블레이드' 스킬 해제` = **19자** (공백·따옴표 포함, "영웅의 "(4) + "'궤도 블레이드' "(9) + "스킬 해제"(5) ≈ 18~19자). 검산: `파멸의 노바`(5자)·`돌진 강타`(4자) 모두 `궤도 블레이드`(6자)보다 짧아 19자가 최장임에 영향 없음.

- 한글 읽기 속도 보수값 ≈ 6~7자/초 (자동전투 중 분할 주의 상태 가정, 일반 묵독 9~10자/초보다 보수적).
- 필요 정독 시간 = 19자 ÷ 6.5자/초 ≈ **2.9초**.
- **텍스트가 화면에 실제로 보이는 총 시간 = 인 0.35 + 홀드 1.2 + 아웃 0.35 = 1.9초.** 슬라이드 인/아웃 구간에도 텍스트는 이미 라벨에 세팅되어 화면 안에 들어오므로(인 후반부터 가독), 실질 가독 시간은 홀드 1.2초보다 길다.
- 홀드 1.2초 단독으로는 정독에 모자라나(2.9s 필요), **고정 포맷의 가변부는 스킬명 한 토막**뿐이다(`영웅의 '___' 스킬 해제` 의 앞뒤 정형구는 매번 동일 → 실제로 새로 읽을 정보는 따옴표 안 4~6자). 그 가변부만의 정독 시간 = 6자 ÷ 6.5 ≈ 0.9초로 홀드 1.2초 안에 든다. 더해 **반복 노출**(한 런 3회, 같은 풀 영웅이 매 런 같은 스킬)로 패턴 인지가 빨라진다. 정독 100%가 목적이 아니라 "무슨 스킬인지 식별"이 목적이므로 인+홀드+아웃 1.9초 노출은 충분. 홀드를 2.9초로 늘리면 끊김 체감이 과해진다(3회 누적 11.7s). **1.2s 확정.**

## 2. 카메라 쉐이크

### 2.1 결정값 (plan 기본값 유지)

| 항목 | 값 | plan sync |
|---|---|---|
| duration | **0.4s** | 일치 (`ShakeDuration` const, `SkillUnlockCutsceneController`) |
| magnitude | **0.3 월드 유닛** | 일치 (`ShakeMagnitude` const) |
| 감쇠 | **선형** (남은 시간 비례로 진폭 0 까지) | 일치 (plan `ApplyShake` k = remain/duration) |

### 2.2 근거 — 2.5D 탑다운에서 0.3 유닛이 과하지 않은 이유

쉐이크 진폭은 **카메라가 보는 월드 범위 대비 비율**로 판단한다. BattleCamera 는 거리 기반 줌(`_currentDist`)으로 영웅 주변을 비추며, 한 화면에 영웅 + 수렴 몬스터 무리 + ring 둘레가 들어오는 탑다운 구도다. 이 구도에서 화면 세로가 담는 월드 범위는 대략 **10~16 유닛** 수준(영웅 반경 ~0.5, 몬스터 다수가 한 화면에 보이는 거리). 0.3 유닛 진폭은 화면 세로의 **약 2~3%** 흔들림으로, "눈에 띄지만 멀미 없는" 격겜 임팩트 쉐이크의 표준 대역(화면의 1~4%)에 든다.

- **과하지 않은 쪽 근거**: 0.3 유닛은 영웅 캐릭터 한 칸(~0.5~1 유닛)보다 작은 진폭. 화면이 통째로 튀는 게 아니라 살짝 "쿵" 하는 강조. 0.4s 짧은 지속 + 선형 감쇠로 즉시 잦아들어 정지 화면의 가독을 해치지 않는다 (쉐이크 종료 시점에 배너 슬라이드 인이 본격화).
- **부족하지 않은 쪽 근거**: 0.1 유닛 이하면 탑다운 줌 거리에서 거의 인지 불가. 0.3 은 "정지 + 쿵 + 배너 진입" 3박자 중 임팩트를 담당하는 최소 유효 진폭.
- **드리프트 방지**: plan `ApplyShake` 가 매 unscaled 프레임 `basePos + offset` 합성, 종료 시 `offset=0` 복원 → 쉐이크 후 카메라가 어긋난 위치에 굳지 않는다 (spec §5 함정 회피). 이 동작은 락이며 본 기획서는 수치만 확정.

**0.4s / 0.3 유닛 확정.** 조정 불필요.

## 3. 배너 비주얼

### 3.1 화면 세로 위치 — **하단 1/3 (lower-third)**

> **이 결정이 가독성·dim 처리·카드팝업 공존을 모두 가른다.** 먼저 확정.

**결정: 배너 가로 밴드를 화면 세로 중앙이 아니라 하단 1/3 영역(lower-third)에 배치한다.** 구체적으로 밴드 중심 Y = 화면 중앙에서 아래로 내린 위치 (anchoredPosition.y = **-280** , 1280×720 기준 — 카드 레이아웃 하단보다 더 아래로 완전히 비킨 자막 위치. 아래 §3.5 검산).

근거 — **카드 선택 팝업과의 화면 공간 충돌 회피**:

스킬 해금 임계(shipped 85/65/45%)는 패시브 카드픽 트리거(HP 10%마다: 0.9/0.8/0.7/0.6/0.5/…/0.1)와 **정확히 같은 HP 지점에서는 겹치지 않는다** — 85/65/45 는 패시브 임계(0.9·0.8·0.7·0.6·0.5) 각각의 **0.05 아래** 빈 구간에 위치한다(이 0.05 오프셋이 임계 단위의 1차 충돌 회피이며, 의도·SoT 는 `hero-skills.md` §1/§13). 그럼에도 본 기획은 배너 세로 위치로 **2차 회피**를 둔다 — 두 UI 가 같은 순간 떠도 서로 가리지 않게 하는 안전망이다. spec §5 가 카드픽-컷인 중첩을 "허용/드물게 발생"으로 락했으므로 충돌 해소는 재설계하지 않되, **그런 중첩이 발생해도 서로 가리지 않게 배너의 세로 위치를 정하는 것이 본 기획의 책임**이다. (중첩이 일어나는 실제 경로: HP 급락으로 해금 컷인 큐가 카드픽 정지 구간까지 드레인되거나, 인접한 패시브 픽(예 0.9 픽)과 해금(0.85)이 시간상 근접해 정지 연출이 꼬리물기로 겹치는 경우.)

- `CardSelectionPopup` 의 공간 점유(빌더 데이터): 타이틀 "카드 선택"은 **상단**(anchoredPosition.y = -60, 위 앵커), 3장 카드 슬롯(각 320×420, MiddleCenter)은 **화면 정중앙**에서 세로 y ∈ **[-210, 210]** 을 점유(슬롯 높이 420 의 절반 = 210). 즉 카드 콘텐츠는 화면 중앙 ±210 범위.
- 격겜 컷인 관습은 정중앙이 가장 임팩트 크지만, 정중앙은 카드 콘텐츠(±210) 위에 정확히 겹쳐 카드를 가린다.
- **카드 콘텐츠 하단(-210) 보다 더 아래(밴드 상단 ≤ -210)** 로 내리면 카드와 겹치지 않는다. 밴드를 그 아래(자막 위치)에 두면 카드 3장(중앙)·타이틀(상단)을 가리지 않고 공존한다 — 검산 §3.5.

**z-우선순위 요청**: 중첩 시 배너가 카드팝업 위에 보여야 한다(배너가 더 짧고 명시적 알림). 배너 팝업은 카드팝업보다 **나중에/위 레이어로 표시**되도록 구현 요청 (§7 참조).

스킬 해금이 단독으로 뜰 때(HP 45% 등)도 하단 1/3 은 영웅 전투 화면(중앙)을 가리지 않아 "정지된 전투 위에 알림 띠가 지나간다"는 깔끔한 연출이 된다.

> **[정정 노트 — 두 회피 레이어 정합] 임계 오프셋 ↔ 배너 위치.** 카드픽-컷인 충돌에는 **독립된 두 회피 레이어**가 있고, 본 정정으로 둘이 모순 없이 정합된다.
> - **① 임계 오프셋 (1차, `hero-skills.md` SoT)**: shipped 게이트 85/65/45 가 패시브 임계 0.9/0.8/0.7/0.6/0.5 에서 각 0.05 아래로 비켜 있어, 해금 컷인과 카드픽이 *같은 HP 순간에* 동시 발동하는 경우를 줄인다. 이 의도·SoT 는 `hero-skills.md` §1/§13(에셋 값 + 커밋 `688a649` 역추론)이 단일 진실이며, **본 문서는 이 레이어를 정의하지 않고 그 결과(85/65/45)만 인용**한다.
> - **② 배너 위치 (2차, 본 문서 SoT)**: 그래도 큐 드레인·꼬리물기 등으로 두 UI 가 겹쳐 뜨면 배너를 카드 콘텐츠(±210) 아래 자막(y=-280)에 두어 시각적으로 가리지 않게 한다.
> 두 레이어는 **상호 배타가 아니라 직렬 안전망**이다 — ①이 동시 발동 빈도를 낮추고, ②가 그래도 겹친 케이스를 시각적으로 흡수한다. (`hero-skills.md` §1/§13 의 self-review 가 "cutscene 기획서는 겹침 허용 + 배너 위치 회피를 택한다"고 한 것은 본 ② 레이어를 가리키며, 본 문서의 임계 표기가 90/70/50 → 85/65/45 로 정합되면서 두 문서의 임계·페이즈 매핑이 1:1 일치하게 됐다.)

### 3.2 밴드 자체가 대비 표면 — 별도 전체 dim 없음

**결정: 전체화면 dim 레이어를 두지 않는다. 배너 가로 밴드 자체를 불투명에 가까운 대비 표면으로 만들어 그 위 텍스트 가독을 확보한다.**

근거 (YAGNI + 중첩 안전):
- 컷인은 ~1.9초로 짧다. 전체 dim 은 ~2초짜리 알림에 과한 무게이며, 정지된 전투 화면 전체를 어둡게 덮으면 "영웅이 어디까지 강해졌나"라는 정지 순간의 정보(몬스터 포위 상황)를 오히려 가린다.
- 카드팝업과 중첩 시 카드팝업이 이미 자체 dim `Color(0,0,0,0.65)` 를 깐다. 배너가 또 전체 dim 을 깔면 **dim 이 이중**으로 쌓여 과도하게 어두워진다.
- 따라서 가독은 **밴드 밴드 영역 안에서만** 해결한다 — 밴드를 충분히 불투명하게.

### 3.3 밴드 색/투명도/테두리

기존 UI 톤(CardSelectionPopup dim `0.65` / 카드 하단 Scrim `0.6` / 결과 dim `0.5`)과 일관된 **어두운 반투명 계열**을 쓰되, 밴드는 텍스트 대비 표면이라 더 불투명하게 간다.

| 요소 | 값 | 근거 |
|---|---|---|
| 밴드 배경색 | **`Color(0, 0, 0, 0.82)`** (RGBA, 거의 검정 불투명) | 기존 Scrim 0.6 보다 진하게 — 전체 dim 없이 밴드 단독으로 텍스트 가독 확보. 0.82 면 뒤 전투 화면이 희미하게 비쳐 "정지된 전투 위 띠" 맥락은 유지하되 흰 텍스트는 또렷. |
| 밴드 테두리 | **상·하 가장자리 액센트 라인 1줄** — 색 `Color(1, 0.85, 0.3, 1)` (따뜻한 골드), 높이 **3px** (1280×720 기준) | 격겜 컷인의 "띠가 지나간다" 느낌을 주는 최소 장식. 골드는 "영웅이 강해짐(위협 상승)"을 색으로 암시. 좌우 테두리는 두지 않음(가로 풀폭이라 화면 밖). YAGNI — 코너/그라데이션 등 추가 장식 없음. |
| 밴드 가로 | **화면 풀폭** (좌우 stretch, width = 화면 폭) | spec §3-1 "풀폭 가로 밴드" 락. |
| 밴드 세로 높이 | **120px** (1280×720 기준) | 폰트 44px(아래) + 상하 여백 ≈ 38px씩. 텍스트가 띠 안에서 답답하지 않게. |

### 3.4 라벨 (CHText) — 폰트/색/정렬

Rule 03 §3 준수 — `TextMeshProUGUI` + `CHText` 동반(빌더가 부착). 외부는 `_label.SetText(...)` 의도 API 만 사용.

| 요소 | 값 | 근거 |
|---|---|---|
| 폰트 크기 | **44px** (1280×720 기준) | 기존 톤: 카드 선택 타이틀 48 / 카드명 32 / 버튼 36. 배너는 한 줄 알림이라 타이틀(48)보다 약간 작은 44 — 풀폭 한 줄에서 임팩트와 줄바꿈 방지(19자가 한 줄에 들어감) 균형. |
| 색 | **흰색 `Color.white`** | 기존 모든 강조 텍스트와 동일(타이틀·결과·카드명 전부 흰색). 어두운 밴드(0.82) 위 최대 대비. |
| 정렬 | **가로 중앙 · 세로 중앙** (`TextAlignmentOptions.Center`) | 풀폭 밴드 중앙에 한 줄. 좌측/우측 정렬은 슬라이드 방향과 혼동 유발 → 중앙. |
| 줄바꿈 | **단일 줄** (밴드 폭 충분, 최장 19자) | 밴드 풀폭(1280)에 폰트 44 한 줄 19자 ≈ 700px (44 × 0.83평균자폭 × 19 ≈ 694) ≪ 1280 → 충분히 수용. 검산 §3.5. |
| 빈 이름 fallback | `영웅의 새 스킬 해제` | spec 락. 컨트롤러 `Format()` 가 `string.IsNullOrEmpty` 시 반환(plan Task6). |

### 3.5 치수 검산 (1280×720 기준 — Battle 씬 CanvasScaler referenceResolution)

> Battle 씬·LairUIPrefabBuilder 의 CanvasScaler ref = **1280×720** (1920×1080 아님 — `Battle.unity:1383`, `LairUIPrefabBuilder.cs:47` 확인). 모든 px 단정은 이 좌표계.

- **화면 폭** = 1280. 밴드 풀폭 = 좌우 stretch → width = 1280.
- **밴드 높이** 120 = 폰트 44 + 상여백 38 + 하여백 38 (44 + 38 + 38 = 120). 검산 통과.
- **텍스트 한 줄 수용**: 최장 19자, 폰트 44px, 한글 평균 자폭 ≈ 0.83em → 19 × 44 × 0.83 ≈ 694px ≪ 밴드폭 1280. 단일 줄 통과(줄바꿈 없음).
- **하단 자막 세로 위치**: 화면 세로 720 → y ∈ [-360, +360]. 카드 슬롯 콘텐츠 하단 = **y = -210** (슬롯 420 의 절반). 밴드가 카드와 겹치지 않으려면 **밴드 상단 ≤ -210** 이어야 한다(두 세로 범위 비겹침 조건: 밴드 top ≤ 카드 bottom). 밴드 높이 120, 중심 y → 밴드 상단 = y + 60. 조건 y + 60 ≤ -210 → **y ≤ -270**. 채택값 **y = -280** → 밴드 범위 [-280-60, -280+60] = **[-340, -220]**. 검산: 밴드 상단 -220 ≤ 카드 하단 -210 → **카드와 겹침 없음** 통과. 밴드 하단 -340 ≥ 화면 바닥 -360 → **화면 안**(바닥 여백 20px) 통과.
- **화면 밖 X 오프셋** (`_offscreenX`): plan 기본 **1200**. 밴드 폭 1280 의 절반 = 640. 화면 절반 폭 = 640. 밴드 중심이 +1200 이면 밴드 좌변 = 1200 - 640 = +560 → 화면 우변(+640) 보다 안쪽 **아님**? 검산: 밴드 중심 +1200, 밴드 좌변 = 1200 - 640 = 560. 화면 우변 = +640. 560 < 640 이므로 밴드 좌변이 아직 화면 안(560)에 걸친다 → **완전히 화면 밖이 아님**. **조정 필요**: `_offscreenX` 를 밴드폭(1280) 이상으로 올려 **1300** 으로 한다 (중심 +1300 → 좌변 = 1300-640 = 660 > 640 화면우변 → 완전 화면 밖). **plan delta 발생 — §6 참조.**

## 4. 가독성 — 종합

§3.1(하단 1/3 위치) + §3.2(전체 dim 없음) + §3.3(밴드 0.82 불투명) + §3.4(흰 44px 중앙) 의 결합으로:

- 정지된 전투 배경(밝은 지면·몬스터)이 어떤 색이든, 밴드 0.82 검정 위 흰 텍스트는 대비비가 항상 확보된다 (밴드가 배경을 가리므로 배경색 의존성 제거).
- 카드팝업 중첩 시에도 배너는 하단 1/3 자막 위치(y=-280)가 카드 콘텐츠(±210)와 세로로 비겹침이라 카드/타이틀에 묻히지 않는다.
- 골드 액센트 라인이 밴드 경계를 명확히 해 "어디까지가 알림 띠인지" 시각 분리.

별도 가독성 보강(텍스트 외곽선·그림자) 불필요 — 0.82 밴드만으로 충분. YAGNI.

## 5. 스킬별 색 차등 — **두지 않음 (YAGNI)**

**결정: 스킬마다 밴드/텍스트 색을 다르게 하지 않는다. 3개 스킬 모두 동일 비주얼(검정 0.82 밴드 + 흰 텍스트 + 골드 라인).**

근거:

- 스킬이 3개뿐이고 표시명이 충분히 구별됨(돌진 강타/파멸의 노바/궤도 블레이드). 색 매핑을 추가하면 스킬별 색 SO 필드·빌더 분기·색-스킬 학습 부담이 늘 뿐 식별 이득이 없다.
- MVP 검증 가설은 "스킬 해금을 인지하는가"이지 "스킬 종류를 색으로 변별하는가"가 아니다.
- 향후 스킬이 6+ 로 늘고 아이콘이 들어가면 그때 색/아이콘 차등을 재검토(승격 트리거). 현 단계는 단일 비주얼.
