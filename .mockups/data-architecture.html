2. 저장·로드 흐름

부팅 / 마을 진입JSON 73개 → CHMResource Addressables 로드 → 로더 한 곳(ChapterDatabaseLoader)이 각 Build() 로 검증 후 Current 에 보관. SO(카드 풀 등)는 필요한 곳이 따로 로드
→
진행 데이터MetaProfileStore.Load() → MetaProfileMigration (Version < 13 이면 승격) → MetaSession.Profile
→
전투 1판RunSummary 메모리 누적 → 결과창에서 Profile 갱신 → Store.Save() 즉시 파일 기록
클라우드 백업CloudSaveService.BackupAsync → saves/{uid} 트랜잭션. serverVersion 타임스탬프 불일치 = Conflict → 배지·복원 권유 UX
↔
복원RestoreAsync → 서버 profile 을 로컬에 덮어씀. 데일리 날짜별 기록만 MergeDailyFrom 으로 병합
→
랭킹Easy 챕터 승리 → leaderboard + stageLeaderboard. 데일리 종료 → dailyLeaderboard. 탑 리더보드는 승격만 되고 클라이언트 코드 미구현

정적 데이터 로드 순서와 실패 처리 (ChapterDatabaseLoader.LoadAsync)

순서묶음설명
1필수 전투 밸런스 (BalanceConfig·MonsterStat)로드·검증 실패 시 즉시 중단 - 필수 묶음 4개 Current 와 ChapterDatabase.Current 까지 전부 null
2필수 영웅 스킬 3종 파싱행만 먼저 보관 (검증은 영웅 직업이 정해지는 4번에서)
3챕터 12종ChapterDatabase.Build - 카드 트리거 HP 비율·스킬 해금 HP 비율은 1·2번 JSON 에서 받아 대조 (하드코딩 사본 없음)
4필수 영웅 스킬 검증HeroArchetype_Skill.heroId 가 HeroArchetype 에 있는지 등 → HeroSkillDatabase.Current
5선택 묶음난이도 → 유물 → 편성 → 등급 연출 → 도감 → 쇼케이스 → 탑 → 데일리 → 육성 재화. 실패해도 그 기능만 꺼진다 (기존 동작 그대로)
6필수 카드 (Card·Card_Param)→ CardDatabase.Current
7필수 마을 성장 9종→ MetaConfig.Current. 성공하면 육성 상점 항목 무결성을 1회 검사 (위반은 육성 재화 기능만 끔)
필수 묶음 = 밸런스·영웅 스킬·카드·마을 성장. 하나라도 로드·검증에 실패하면 로더가 위반을 전부 로그로 남기고 4개의 Current 를 함께 null 로 되돌린다 (밸런스 실패일 때만 ChapterDatabase.Current 도 null - 그 외 실패에서는 마을이 쓰도록 유지). 전투 진입 시 BattleController 의 명시 가드가 밸런스·영웅 스킬·메타 중 null 이 있으면 기본 스탯으로 진행하지 않고 마을로 복귀한다 (4개가 함께 초기화되므로 이 3개 검사로 카드 실패까지 막힌다). 챕터 JSON 단독 실패 시 기존 동작은 이번에 바꾸지 않았다.
카드 풀 SO 와 Card.json 의 일치, Card_Species 의 카드 id 대조는 런타임이 아니라 EditMode 테스트가 맡는다 (런타임은 Card_Species.cardId 가 ECardId 값명인지만 본다). 카드 풀 SO 는 로더가 아니라 BattleController·VillageController 가 EData.CardPool_* 로 직접 로드한다.
충돌 감지는 클라이언트가 한다. 서버 검증은 Firestore 보안 규칙 범위까지이며 Cloud Functions 는 없다. 랭킹 쓰기는 "기존보다 빠를 때만" 을 클라이언트 트랜잭션이 판정한다.

3. 정적 데이터 - JSON (Addressable)

모두 73개 (3.1~3.9). 이번 이전의 신설 16개는 3.7(전투 밸런스·마을 성장 11개), 3.8(영웅 스킬·카드 5개). 공통 규약: 파일명 = EData 값명 = Addressables 주소. 배열은 JsonArrayUtility, 단일 객체는 JsonUtility. 관계 데이터 이름은 <부모>_<관계>. 선택적 관계는 행이 있을 때만 존재(sentinel 없음). Enum 을 가리키는 문자열 필드는 그 Enum 값명 그대로.

9. 키 규약 요약

키 종류규칙
에셋 키Enum 값명 = 파일명 = Addressables 주소 (EData·EMonster·EUI·ERelic …). JSON 안에서 다른 Enum 을 가리킬 때는 값명 문자열.
스테이지JSON 은 chapterId + stageIndex 복합키, 세이브·리더보드는 선형 번호 (chapterId-1)*5 + stageIndex (1~25).
몬스터 등급EMonster 정수 순서로 산술 해석 (MonsterGrades.BaseOf / GradeOf). Race_Monster 는 그 해석과 일치하는지 검증용. 스탯·육성·카드는 전부 기준 몬스터 행을 공유.
문자열UI 문구는 전부 Strings_Ko.id(int) 참조. 데이터 로드 시 nameKey 존재 여부까지 검증. 상점·도전과제·영주 보상·영웅 스킬·카드의 이름·설명도 이제 인라인 문자열이 아니라 1541~1687 id.
세이브 키 (글자 불변)ShopItem.itemId (= ShopLevels[].ItemId) · Achievement.achievementId (= AchievedIds[]) · Card.cardId = ECardId 값명 (= PickedCards[]·CardPickCounts[]). JSON 행을 고쳐도 이 id 는 바꾸지 않는다 - 바꾸면 기존 세이브의 상점 레벨·업적·도감이 끊긴다. 카드는 id 와 효과 이름이 달라도 된다 (effectKind 가 따로).
EData 와 JSON 개수EData 값 수 ≠ JSON 파일 수. 폐기 자리(FormationMonster, HeroSkillLoadout* x5)와 SO 키(CardPool_*, SynergyVisualConfig)가 섞여 있다. JSON 은 Data/Json/ 73개.
선택적 관계 (sentinel 금지)해당하는 항목에만 관계 JSON 행이 있다 (ShopItem_* · LordLevel_Reward · Card_Param). 0·1.0·빈 문자열 같은 가짜 값으로 "없음"을 채우지 않는다.
세이브 엔트리 리스트JsonUtility 제약으로 Dictionary 대신 {Key, Value} 리스트. "없음" 은 행 부재로 표현 (sentinel 은 BestClearTime -1 하나만 레거시).
Firestore 문서 ID유저 1건: {uid}. 유저 x 축 1건: {stage}_{uid}, {day}_{uid}. 전역 유일성 락: {normalizedName}.
버전MetaProfile.Version 13 = 저장 스키마. Firestore schemaVersion 에 그대로 복사. 로드 시 MetaProfileMigration 이 올린다(내리지 않음).
